# 기존 주문 최적화 프로토타입의 병합 가능성 검토

검토일: 2026-09-23 · 대상: [`hobumleo-del/-`](https://github.com/hobumleo-del/-)의 `main` 브랜치

## 결론

기술적으로 병합 또는 선택적 코드 이전이 가능하다. 이 신규 프로젝트는 기존 저장소에서 분기하지 않았으므로 Git 공통 조상이 없다. 나중에 전체 이력을 합치려면 별도 Git 작업이 필요하고, 신규 프로젝트의 `README.md`와 기존 저장소의 `README.md`는 같은 경로이므로 충돌할 수 있다. 현재는 어느 저장소에도 병합을 수행하지 않았다.

실무적으로는 기존 `index.html`의 수동 주문계산 화면·로직을 필요한 부분만 검토해 신규 서비스에 옮기는 편이 적합하다. 기존 파일을 그대로 합치는 것만으로 새 사양의 웹 서비스가 되지는 않는다.

## 확인한 기존 구조

- 공개 저장소이며 기본 브랜치는 `main`이다.
- 확인된 파일은 `README.md`와 단일 `index.html`이다. 기존 README는 제목 한 줄이다.
- `index.html`은 부족 품목, 거래처, 도매가격, 추가 후보를 수동 입력하고 주문안을 계산하는 단일 페이지다.
- 입력자료는 브라우저 `localStorage`에 저장된다. 로그인·공유 서버·POS 파일 업로드·입고장 촬영·재고 원장은 확인되지 않았다.
- 현 로그인 계정은 기존 저장소에 읽기 권한만 있다. 브랜치 생성 시 GitHub가 403 응답을 반환했다.

## 이전 가능한 부분과 재설계할 부분

| 영역 | 판단 | 이유 |
|---|---|---|
| 수동 입력 화면·주문안 표시 | 참고 또는 일부 이전 가능 | 신규 서비스의 발주 담당자 화면을 설계할 때 사용 가능 |
| 상품명 유사검색·거래처 이력 아이디어 | 데이터 규칙 검증 후 일부 이전 가능 | SKU·규격·바코드와 약국별 권한을 적용해야 함 |
| MOQ·최소주문금액 계산 | 테스트와 규칙 분리 후 재사용 검토 | 도매상별 상품군·세금·프로모션·배송 일정이 신규 사양에 추가됨 |
| 브라우저 `localStorage`를 원본 저장소로 사용하는 방식 | 그대로 이전 부적합 | 여러 기기의 동시 사용과 기록·복구 요건을 충족하지 않음 |
| 단일 HTML 파일 전체 | 그대로 이전 부적합 | 계정·서버 검증·파일 처리·실시간 공유 구조가 없음 |

## 나중에 병합할 때의 권장 절차

1. 기존 저장소의 변경이 진행 중인지와 코드 이용 권한을 확인한다. 공개 저장소라는 사실만으로 제삼자의 재사용 권한이 자동 확정되지는 않는다.
2. 신규 프로젝트에서 별도 작업 브랜치를 만들고 기존 `index.html`을 비교한다. 필요한 UI·계산 함수를 테스트와 함께 선택적으로 이전한다.
3. 신규 사양의 판매·입고·재고·발주 데이터 모델과 입력·권한 경계를 맞춘다.
4. 기존 README를 덮어쓰지 않는다. 새 프로젝트의 문서가 기준이며, 실제 구현 이후 내용이 맞는지 갱신한다.
5. 실기기 및 사양서 검수 시나리오로 이전 결과를 검증한 뒤 병합한다.

전체 Git 이력을 한 저장소로 합쳐야 하는 목적이 따로 있다면 공통 조상이 없는 브랜치 병합을 검토할 수 있다. 다만 문서와 파일명이 충돌할 수 있고, 새 제품 기능을 자동으로 완성하지 않으므로 코드 재사용 목적에는 선택적 이전이 더 단순하다.
