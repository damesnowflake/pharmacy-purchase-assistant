## 2. 실제 현장 자료가 있어야 정확도를 확정할 수 있는 것 (구현 자체는 완료)

- **D-02 CatPOS 판매 파일 형식**: 사용자가 이전에 제공한 실제 판매내역 표본
  (`TalkFile_판매내역_20260801-20260831.numbers`, 2026년 8월 3,140건 거래·품목상세 4,812건,
  로컬 `~/Downloads`에서만 확인, 저장소·문서에는 원본을 올리지 않음)을 열어 구조를 확인했다.
  **이 파일은 CatPOS가 직접 낸 파일이 아니라 사용자가 Numbers로 저장한 사본이므로, 실제 CatPOS
  CSV/Excel 내보내기와 100% 같다고 단정하지 않는다.** 확인한 내용:
  - 거래 헤더 행(no·판매일자·시간·...·판매상품·...·거래구분 등 17열) 아래에, 그 거래의 품목마다
    `[전각공백]└ 상품명: OOO | 판매단가: N | 할인: N | 수량: N | 판매금액: N` 형식의 "품목 상세"
    텍스트 행이 하나씩 따라붙는 구조였다. 여러 품목이면 헤더 행 "판매상품" 열에는 "OOO 외
    1품목"처럼 요약만 있어, 열 매핑 방식의 범용 가져오기로는 수량을 올바르게 뽑을 수 없다.
  - "거래구분" 열은 반품 여부가 아니라 결제수단(카드사명 등)이었다.
  - 표본 7,954행 전부가 하나도 빠짐없이 두 행 형식(거래 헤더/품목상세) 중 하나로 분류됐다.
  - 전용 파서(`src/lib/catposTalkFileParser.ts`, 헤더로 자동 인식, 아니면 범용 가져오기로 대체)
    로 4,812개 품목상세 전부를 오류 없이 추출했고, **실제 Supabase 프로젝트에 REST API로 180일치
    합성 판매 데이터를 업로드해 회귀모델 학습→추천 생성까지 끝까지 확인했다**(아래 "확인된
    사항" 참고).
  **여전히 확인하지 못한 것**: 그 표본 기간에는 반품·취소 거래가 한 건도 없어 CatPOS가 반품을
  어떻게 표현하는지 여전히 모른다. 전체기간(full_period) 형식만 지원하며 증분(incremental)은
  `NOT_IMPLEMENTED`다(FR-07). 표본 1건만으로 CatPOS의 모든 사용자·버전이 같은 열 구성을
  쓰는지도 확정할 수 없다.
  - **(5차 갱신) 실제 네이티브 CatPOS 파일로 재확인**: 사용자가 실제 매장 CatPOS에서 직접
    내려받은 `판매내역_20260823-20260923.xls`(2026-08-23~09-23, 32일·거래 3,535건·품목상세
    5,430행, 날짜가 문자열이 아닌 엑셀 날짜 일련번호로 저장되어 있어 Numbers 사본이 아닌 진짜
    네이티브 내보내기로 판단)을 같은 파서로 돌려 **5,430행 전부를 오류 0건으로 추출**했다.
    이전 표본(Numbers 사본)과 동일한 열 구조·품목상세 형식임을 실제 파일로 재확인했으므로,
    파서가 실제 CatPOS 출력과 다르다는 근거는 더 이상 없다. 다만 이번 파일에도 반품·취소로
    보이는 음수 수량/금액 행이 전혀 없어, 반품 표현 방식은 여전히 미확인이다.
- **D-04 iPhone 로컬 OCR**: 0020 개선 작업에서 마지막 숫자 추측을 제거하고 좌표·수량 헤더 기반
  추출, 누락 수량 확인, 사진 대조, 같은 화면 상품 검색·등록을 구현했다. 제공된 입고장 열 구조를
  본뜬 합성 좌표 테스트는 통과했다. 사용자 결정에 따라 실제 기기 검수는 배포 차단 조건이 아니다.
  실제 운영 시작 후 1개월 이상 피드백을 모아 OCR 인식률·조작 불편·동기화 문제를 개선한다.
- **D-01 참고값 기본안 / D-03 회귀모델 품질**: 계산 로직은 완성하고 단위 테스트로 설계 문서
  예제를 재현했으며, 이번에 실제 Supabase 프로젝트에서 180일 합성 데이터로 회귀 학습과 참고값
  계산이 실제로 동작함을 확인했다. 다만 실제 판매·입고 자료로 이 기본안(보수적 근사, OLS
  모델)이 현장에서 정확한지는 여전히 검증하지 못했다.

  2026·2027년 대체공휴일 포함 46건의 실제 공휴일 데이터를 정상적으로 받아와 `holiday_dates`에

**상품마스터 적재 규칙(자동 판단, 사용자 확인 전 적용)**:
- 상품명이 유일하면 규격 없이(`spec=''`) 그대로 1개 상품으로 등록.
- 상품명이 같고 제조사도 같은 행(504행)은 등록일시 상관없이 첫 행만 남기고 나머지는 진짜
  중복으로 보고 버렸다.
- 상품명은 같지만 제조사가 다른 경우(56개 상품명, 112개 상품)는 서로 다른 실제 품목으로 보고
  `spec=제조사명`으로 구분해 각각 별도 상품으로 등록했다(예: "갈근탕"이 "신신"/"한미약품(주)"
  두 상품으로).
- 기준단위(`base_unit`)는 마스터 파일에 단위 열이 없어 전부 "개"로 기본값을 두었다(판매내역의
  거래수량이 모두 정수 단위로 보임). `observed_from`은 판매내역 시작일인 2026-08-23으로 뒀다
  (그 이전 관측치는 없다는 뜻이지 "판매 없음"이 아니다 — 상세_알고리즘_설계.md의
  missing/not_observed 구분과 일치).
- 마스터의 "상품종류"(의약품/부외품/화장품/건기식/미지정)는 `products.category`에 그대로
  보관했다(기존에 있었지만 화면·RPC 어디서도 안 쓰던 열 — 참고용으로만 채웠고 새 화면·계산
  로직을 추가하지는 않았다).
- 결과: **3,481개 상품**을 실제 배포 환경에 `create_product` RPC(관리자 세션 인증, 3,481회
  전부 성공)로 등록했다. 실제 Supabase에는 이전 상품이 하나도 없었으므로(순수 신규 배포) 기존
  자료와의 충돌은 없었다.

**판매내역 적재**: 5,430개 품목상세행의 품목명 820종 중 801종(97.7%)이 위 상품마스터와
공백/대소문자 정규화 후 정확히 일치했다. 나머지 19종은 위에서 제조사로 구분한 "상품명은 같지만
서로 다른 상품" 그룹과 겹쳐 판매내역만으로는 어느 제조사 상품인지 구분할 수 없었다(예: 판매내역에
"액티피드정"만 있고 제조사 정보가 없음). **이 19종·119행(전체의 2.2%)은 어느 쪽에도 임의로
배정하지 않고 그대로 미반영 처리했다** — 잘못된 상품에 판매 이력을 붙이는 것이 안 붙이는 것보다
더 나쁘다고 판단했다. 해당 19개 상품명 목록과 스킵된 행 수는 이 세션의 실행 로그에 남아 있다.
사용자가 두 제조사 상품 중 하나로 합치거나(중복 상품 비활성화) 수동으로 배정하길 원하면 알려달라.
- `begin_sales_import`→`stage_sales_rows`→`commit_sales_import` RPC로 실제 배포 환경에
  적용: **5,430행 중 5,311행 반영, 119행 스킵**(위 사유), 영향받은 상품 801개.
- 최초 실행에서 상품 목록 조회 시 PostgREST 기본 페이지 크기(1,000행)를 넘는 걸 놓쳐 3,481개
  중 972개만으로 매칭한 실제 버그를 발견 — 커밋된 `sales_daily`/`sales_coverage`/
  `sales_imports` 행을 전부 지우고 페이지네이션을 고쳐 처음부터 다시 실행해 위 정확한 결과를
  얻었다(도중에 저장된 잘못된 중간 결과는 남아 있지 않다).
- `forecast-batch` 엣지 함수를 40회 반복 호출(배치당 최대 20개)해 `recompute_queue`에 쌓인
  801개 상품을 전부 처리, `forecast_models`에 801개 회귀모델이 실제로 학습됨을 DB로 확인했다.
- **추천(`recommendations`)은 아직 0건이다** — 이는 버그가 아니라 예상된 상태다. 추천을 내려면
  판매 예측 외에 현재 대기수량(`product_state.pending_qty`, 입고·발주·실사 이벤트로 채워짐)이
  필요한데, 아직 실제 입고·실사 자료를 하나도 등록하지 않았기 때문이다. 약국에서 입고 등록·실사
  입력을 시작하면 그때부터 추천이 생성된다.

### 의존성 보안
npm 레지스트리의 `xlsx` 0.18.5(알려진 프로토타입 오염·ReDoS 취약점)를 SheetJS 공식 CDN 패치
버전(0.20.3)으로 교체했고, `react-router-dom`도 open-redirect 이슈가 있는 6.x에서 7.18.4로
올렸다. 남은 취약점(vite/vitest)은 개발 도구 전용이라 배포 결과물에는 포함되지 않는다.
