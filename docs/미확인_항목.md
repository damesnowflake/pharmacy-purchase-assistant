# 구현 중 미확인·차단 항목

작성일 2026-09-23 (2차 갱신). 이 문서는 실제 계정·API 키·현장 표본이 있어야만 확정할 수 있는
항목을 모아 둔 목록이다. 아래 항목이 해결되지 않은 기능은 코드 상에서도 "완료"로 표시하지
않았다 (TODO 주석, 예외를 던지는 자리표시자 RPC, 비활성화된 UI 버튼, "검증되지 않음" 문구 등).

## 1. 외부 계정·서비스 연결이 필요해 지금 진행할 수 없는 것

- **Supabase 프로젝트 생성**: 아직 생성되지 않았다. 생성 후 `SUPABASE_URL`,
  `VITE_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`를 받아야 `supabase/migrations`
  0001~0010을 적용하고 프론트를 실제로 로그인·데이터 연동 시험할 수 있다. 로컬 개발에는
  Supabase CLI(`supabase start`, Docker 필요)도 필요하며 이번 개발 환경에는 설치되어 있지
  않다 (`supabase not found`, Docker 없음).
- **공휴일 API 키**: 공공데이터포털 "한국천문연구원 특일 정보"(`getHoliDeInfo`) 서비스 키가
  없으면 `supabase/functions/holiday-sync`를 실제로 호출해 볼 수 없다. 엔드포인트·파라미터·
  응답 필드명은 공공데이터포털 문서로 확인해 코드에 반영했지만, 실제 키로 호출·응답 형식을
  확인한 적은 없다 (IR-09).
- **Cloudflare 계정 연결**: `wrangler.toml`과 `.github/workflows/deploy.yml`(수동 실행,
  `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID`/`VITE_SUPABASE_*` 시크릿 필요)을 준비했지만
  실제로 배포해 본 적이 없다. **따라서 지금 시점에 실제 서비스 주소(URL)는 없다.**
- **pg_cron / pg_net 실제 등록**: `0008_maintenance_and_capacity.sql`의 일일 유지보수 예약과
  holiday-sync/forecast-batch의 정기 실행은 실제 Supabase 프로젝트(pg_cron·pg_net 기본 제공)
  에서만 등록된다. 로컬 스모크 테스트 환경에는 이 확장이 없어 "건너뜀" 경로만 검증했다.
  holiday-sync·forecast-batch를 pg_cron+pg_net으로 매일 자동 호출하려면 실제 프로젝트에서
  Edge Function URL과 anon/service 키를 알아야 하므로, 이 SQL은 저장소에 아직 추가하지 않았고
  [개발_환경_설정.md](개발_환경_설정.md)에 수동 설정 절차만 적어 두었다.

## 2. 실제 현장 자료가 있어야 정확도를 확정할 수 있는 것 (구현 자체는 완료)

- **D-02 CatPOS 판매 파일 형식**: 사용자가 이전에 제공한 실제 판매내역 표본
  (`TalkFile_판매내역_20260801-20260831.numbers`, 2026년 8월 3,140건 거래·품목상세 4,812건,
  로컬 `~/Downloads`에서만 확인, 저장소·문서에는 원본을 올리지 않음)을 이번에 직접 열어
  구조를 확인했다. **이 파일은 CatPOS가 직접 낸 파일이 아니라 사용자가 Numbers로 저장한
  사본이므로, 실제 CatPOS CSV/Excel 내보내기와 100% 같다고 단정하지 않는다.** 확인한 내용:
  - 거래 헤더 행(no·판매일자·시간·...·판매상품·...·거래구분 등 17열) 아래에, 그 거래에 포함된
    품목마다 `[전각공백]└ 상품명: OOO | 판매단가: N | 할인: N | 수량: N | 판매금액: N` 형식의
    "품목 상세" 텍스트 행이 하나씩 따라붙는 구조였다. 거래에 품목이 여럿이면 헤더 행의
    "판매상품" 열에는 "OOO 외 1품목"처럼 요약만 있고, 실제 품목별 수량은 상세 행에만 있다 —
    즉 열 매핑 방식의 범용 가져오기로는 이 구조에서 수량을 올바르게 뽑을 수 없다.
  - "거래구분" 열은 반품 여부가 아니라 결제수단(카드사명 등)이었다.
  - 표본 7,954행 전부(헤더 1 + "총 N건" 합계 1 + 거래 헤더 3,140 + 품목상세 4,812)가 하나도
    빠짐없이 이 두 가지 행 형식 중 하나로 분류됐다.
  - **이 파일 그대로(가상의 데이터가 아니라 실제 내용)를 CSV로 내보내 만든 파서
    (`src/lib/catposTalkFileParser.ts`)에 넣어 4,812개 품목 상세 전부를 오류 없이 추출하고,
    사입 검토 파이프라인(품목 매칭→분류→기간 산출→날짜 공백 확인)까지 끝까지 통과시켰다.**
  이 구조를 인식하면(`detectCatposTalkFileColumns`) 열 매핑 단계 없이 자동으로 이 전용
  파서를 쓰고, 인식하지 못하면 기존의 범용 CSV/XLSX 열 매핑 가져오기로 대체한다.
  **여전히 확인하지 못한 것**: 이 표본 기간(2026년 8월)에는 반품·취소 거래가 단 한 건도 없어,
  CatPOS가 반품을 어떻게 표현하는지(별도 거래로 음수 처리하는지, 품목 상세에 표시하는지 등)는
  여전히 모른다 — 지금은 상세 행의 수량을 항상 그대로(양수 가정 없이 파싱된 값 그대로) 반영한다.
  전체기간(full_period) 형식만 지원하며, 증분(incremental) 형식은 여전히 `NOT_IMPLEMENTED`다
  (FR-07 — 실제 증분 식별자 방식이 확인되지 않았기 때문). 또한 이 표본 1건만으로 CatPOS의 모든
  사용자·버전이 같은 열 구성을 쓰는지도 확정할 수 없다.
- **D-04 iPhone 로컬 OCR**: 촬영/사진 선택 → 기기 내 Tesseract.js(kor+eng) 인식 → 줄 단위로
  품목·수량 후보 추출 → 직원이 확인·수정 → 저장까지 전체 파이프라인을 구현했다(더 이상
  비활성 버튼이 아니다). 사진과 OCR 원문은 서버로 전송하지 않으며 인식 후 이미지 URL과 워커를
  해제한다. 다만 **"줄 끝의 숫자를 수량으로 본다"는 v1 규칙의 실제 인식 정확도는 검증되지
  않았다** — 이번에 로컬 환경(`~/Downloads`, `~/Pictures` 등)에서 이전에 제공됐다는 "5종
  입고장 이미지"를 찾아봤지만 실제로는 존재하지 않았고(찾은 것은 판매내역 Numbers 파일과 무관한
  사진 1장뿐), iPhone 실기기도 없다. 그래서 모든 OCR 결과는 직원이 반드시 품목을 선택하고
  수량을 확인해야만 저장 목록에 담기도록 만들었다(자동 확정 없음).
- **D-01 일 경계 기본안 검증**: 실사·최근입고 기준 참고값 계산은 `src/lib/inventoryAnchor.ts`와
  `supabase/functions/forecast-batch`에 모두(최근입고 경로 + 실사 경로, 장중 보정 포함)
  구현했고 단위 테스트로 설계 문서 예제를 재현했다. 실제 판매·입고 자료로 이 보수적 근사가
  현장에서 쓸 만한지는 아직 검증하지 못했다.
- **D-03 회귀모델 품질**: OLS 모델과 `timeSeriesBacktest`(MAE/WAPE 시간순 검증) 함수는 준비돼
  있지만, 실제 판매자료로 백테스트를 돌려 모델이 실전에 쓸 만한지는 확인하지 못했다.

## 3. 코드 상 알려진 미완성 (완료로 표시하지 않음)

- **거래처별 발주조건(purchase_terms) 개별 편집 화면**: DB·RPC(`save_purchase_terms`)는 있고
  로컬 SQL 테스트로 동작을 확인했지만, 품목별로 거래처 조건을 고르는 화면은 아직 연결하지
  않았다(설정 화면은 품목 기본 MOQ/발주단위, 거래처 최소금액·휴무일까지만 연결함).
- **RLS·RPC의 실제 Supabase 연동 시험**: Auth·PostgREST·Realtime·Edge Functions을 실제
  프로젝트에 붙여 시험한 적은 없다. 로컬 PostgreSQL로 검증한 범위는 아래 "4. 확인된 사항"을
  참고 — 그 시험은 DB 로직 시험이며 Supabase의 인증·API·실시간 계층 자체를 검증한 것은
  아니다.
- **holiday-sync·forecast-batch Edge Function 실제 배포**: 코드는 완성했고 esbuild로 구문
  오류가 없음을 확인했지만, 실제 Supabase 프로젝트에 `supabase functions deploy`로 배포해
  실행 로그를 본 적은 없다(Deno 런타임 자체를 이 환경에서 실행할 수 없음).
- **Cloudflare Pages 실제 배포**: 위 "1." 참고. 서비스 주소 없음.
- **계정 발급 스크립트**: 실제 서비스 키로 실행해 본 적 없음.

## 4. 확인된 사항 (실제로 검증 완료)

- **순수 계산 로직**: `src/lib/*.ts` 61개 vitest 테스트(날짜/도착일 8, 추천수량 5, 대기량 7,
  참고값 2, 회귀모델 5, 판매파일 파싱·행 분류·인코딩 23, CatPOS 톡파일 파서 9, OCR 행 추출 5,
  retention/ranking 로직 포함)가 모두 통과하며, 개발계획.md·상세_알고리즘_설계.md의 숫자 예제
  (토요일→화요일 도착, MOQ10·7일수요23·단위6→24, 발주10→입고6→4→0, 입고100-판매80-예측20=0
  등)를 그대로 재현한다.
- **DB 마이그레이션 0001~0010 전체**가 로컬 PostgreSQL 16(임시 인스턴스, `auth.users`/
  `auth.uid()`/anon·authenticated 역할만 최소 스텁)에 처음부터 순서대로 오류 없이 적용된다.
  다음을 실제 SQL 실행으로 확인했다:
  - 비활성 계정 RPC 거부, 관리자 전용 RPC의 직원 호출 거부, 버전 충돌(VERSION_CONFLICT)
  - 멱등성(같은 request_id 재시도는 같은 결과, 다른 내용 재시도는 REQUEST_CONFLICT)
  - 발주10→입고6→입고4 사건에서 대기량이 설계 문서 표와 동일하게 10→4→0으로 변화
  - RLS 조회 권한: 활성 계정만 조회 가능, 비활성 계정은 0건, `anon`은 permission denied
  - **판매 업로드 전체 흐름**: 같은 품목·날짜 2행 합산, 미매칭 행 건너뛰기, 같은 파일 재적용
    거부(DUPLICATE_FILE), 겹치는 기간의 다른 파일 업로드 시 그 기간만 정확히 교체(다른 기간의
    기존 자료는 보존), 커밋 후 임시 적재행 정리, 영향받은 품목의 recompute_queue 등록
  - **180일 롤업**: 200~190일 전 판매(11일×10=110)가 `rollup_old_sales_daily()` 한 번으로
    `sales_rollups`에 반영되고 원본 행이 삭제됨, 재실행해도 중복 합산되지 않음(멱등성)
  - **만료된 스테이징 업로드 정리**(`expire_stale_sales_imports`)와 **용량 점검**
    (`capacity_status`, 관리자 전용) 정상 동작
  - **재계산 큐(FR-28) 연결**: 입고 등록·발주 확정/취소·품목 설정·거래처 조건·거래처 휴무일
    변경이 모두 해당 품목을 `recompute_queue`에 등록하는지 확인
  - 이 과정에서 실제 버그 2건을 발견해 수정했다:
    1. RLS 정책만 있고 `authenticated` 역할에 테이블 `SELECT` GRANT가 없어 모든 조회가
       permission denied로 실패했던 문제 (`0005_permissions_rpc.sql`에 GRANT 블록 추가)
    2. `confirm_order`가 발주일을 자정 시각으로 저장해, 같은 날 그보다 먼저 등록된 입고보다
       시간순으로 앞서 계산되어 대기량이 잘못 산출되던 문제 (발주 확정 시각을 함께 반영하도록
       수정, `0009_recompute_triggers.sql`)
- **판매 업로드 오류 처리(FR-06) 재검토**: 처음 구현에서는 품목은 확인됐지만 날짜·수량을
  해석할 수 없는 행을 화면에 개수만 표시하고 저장에서는 조용히 제외했다 — 지적을 받고
  `classifySalesRows`로 분리해 다시 검증했다. 이제는 그런 행을 "blocking"으로 분류해 값을
  고치거나 명시적으로 제외해야만 저장 버튼이 활성화된다(21개 단위 테스트로 이 경계를
  확인: 품목 없음/날짜 해석 불가/수량 해석 불가 각각 blocking, override로 고치면 valid,
  체크박스로 제외하면 별도 집계). 또한 선언한 판매 기간 안에 자료가 전혀 없는 날짜는
  "실제 무판매"인지 "파일 누락"인지 구분할 수 없으므로(`findDateGaps`) 사용자가 명시적으로
  확인해야만 그 기간을 완료로 커밋할 수 있게 했다.
- **실제 표본으로 다시 찾은 인코딩·날짜 버그 2건** (위 CatPOS 표본을 실제로 CSV로 내보내
  `src/features/sales/SalesUploadPage.tsx`가 쓰는 것과 동일한 코드 경로로 파싱해 봄):
  1. SheetJS에 CSV 원시 버퍼를 그대로 넘기면 BOM 없는 UTF-8을 다른 코드페이지로 오인식해
     한글 헤더·품목명이 전부 깨졌다. 이제는 UTF-8을 먼저 시도하고 실패하면 EUC-KR(Windows
     한글 POS 소프트웨어에서 흔함)로 폴백해 직접 디코드한다(`decodeCsvBytes`).
  2. `cellDates:true`로 CSV의 날짜 텍스트를 JS Date로 바꾸면, 브라우저가 그 문자열을 로컬
     시간대로 해석해 자정 값이 하루 밀렸다(예: "2026-08-31 00:00:00"이 UTC 기준
     "2026-08-30"으로 읽힘). `cellDates:false`로 바꿔 엑셀 일련번호·원문 문자열만 받고, 이미
     시간대와 무관하게 동작을 확인해 둔 `excelSerialToIsoDate`/정규식 파서가 처리하게 했다.
  실제 표본 7,954행 전체를 이 수정된 경로로 다시 파싱해 품목상세 4,812건이 오류 없이,
  올바른 날짜로(예: 마지막 거래가 정확히 "2026-08-31") 추출됨을 확인했다.
- **프론트엔드**: `npm run build`/`lint`/`typecheck`/`test` 모두 통과. 로그인 화면이 데스크톱·
  375px 모바일 뷰포트에서 콘솔 오류 없이 렌더링됨을 브라우저로 확인했다. `xlsx`·
  `tesseract.js`는 동적 import로 분리해 초기 번들에 포함되지 않는다.
- **의존성 보안**: npm 레지스트리의 `xlsx` 0.18.5는 알려진 취약점(프로토타입 오염, ReDoS)이
  있어 SheetJS가 공식 권장하는 CDN 패치 버전(0.20.3)으로 교체했다. `react-router-dom`도
  알려진 open-redirect 이슈가 있는 6.x에서 패치된 7.18.4로 올렸다. 남은 취약점(vite/vitest)은
  빌드·테스트 도구 전용(dev dependency)이라 배포 결과물에는 포함되지 않는다.

## 5. 서비스 주소

아직 없다. Cloudflare Pages 프로젝트를 만들고(계정 연결 필요) `wrangler.toml` 설정대로
`dist`를 배포하거나 `.github/workflows/deploy.yml`을 수동 실행하면 배포된다. 배포 전에
Supabase 프로젝트를 먼저 만들어 `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`를 GitHub
저장소 시크릿(빌드용)과 Cloudflare Pages 환경변수(런타임용, 정적 SPA라 실제로는 빌드 시점에
번들에 포함됨)에 넣어야 한다.
