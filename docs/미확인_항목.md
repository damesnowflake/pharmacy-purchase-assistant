## 2. 실제 현장 자료가 있어야 정확도를 확정할 수 있는 것 (구현 자체는 완료)

- **D-02 CatPOS 판매 파일 형식**: 사용자가 이전에 제공한 실제 판매내역 표본
  (`TalkFile_판매내역_20260801-20260831.numbers`, 2026년 8월 3,140건 거래·품목상세 4,812건,
  로컬 `~/Downloads`에서만 확인, 저장소·문서에는 원본을 올리지 않음)을 열어 구조를 확인했다.
  **이 파일은 CatPOS가 직접 낸 파일이 아니라 사용자가 Numbers로 저장한 사본이므로, 실제 CatPOS
  CSV/Excel 내보내기와 100% 같다고 단정하지 않는다.** 확인한 내용:
  - 거래 헤더 행(no·판매일자·시간·...·판매상품·...·거래구분 등 17열) 아래에, 그 거래의 품목마다
    `[전각공백]└ 상품명: OOO | 판매단가: N | 할인: N | 수량: N | 판매금액: N` 형식의 "품목 상세"
    텍스트 행이 하나씩 따라붙는 구조였다. 여러 품목이면 헤더 행 "판매상품" 열에는 "OOO 외
    1품목"처럼 요약만 있어, 열 매핑 방식의 범용 가져오기로는 수량을 올바르게 뽑을 수 없다.
  - "거래구분" 열은 반품 여부가 아니라 결제수단(카드사명 등)이었다.
  - 표본 7,954행 전부가 하나도 빠짐없이 두 행 형식(거래 헤더/품목상세) 중 하나로 분류됐다.
  - 전용 파서(`src/lib/catposTalkFileParser.ts`, 헤더로 자동 인식, 아니면 범용 가져오기로 대체)
    로 4,812개 품목상세 전부를 오류 없이 추출했고, **실제 Supabase 프로젝트에 REST API로 180일치
    합성 판매 데이터를 업로드해 회귀모델 학습→추천 생성까지 끝까지 확인했다**(아래 "확인된
    사항" 참고).
  **여전히 확인하지 못한 것**: 그 표본 기간에는 반품·취소 거래가 한 건도 없어 CatPOS가 반품을
  어떻게 표현하는지 여전히 모른다. 전체기간(full_period) 형식만 지원하며 증분(incremental)은
  `NOT_IMPLEMENTED`다(FR-07). 표본 1건만으로 CatPOS의 모든 사용자·버전이 같은 열 구성을
  쓰는지도 확정할 수 없다.
- **D-04 iPhone 로컬 OCR**: 전체 파이프라인(촬영→인식→확인→저장)을 구현했지만, 실제 입고장
  사진(이전에 제공됐다는 "5종 입고장 이미지"를 `~/Downloads`, `~/Pictures` 등에서 찾아봤으나
  없었다)도 iPhone 실기기도 없어 인식 정확도는 검증하지 못했다.
- **D-01 참고값 기본안 / D-03 회귀모델 품질**: 계산 로직은 완성하고 단위 테스트로 설계 문서
  예제를 재현했으며, 이번에 실제 Supabase 프로젝트에서 180일 합성 데이터로 회귀 학습과 참고값
  계산이 실제로 동작함을 확인했다. 다만 실제 판매·입고 자료로 이 기본안(보수적 근사, OLS
  모델)이 현장에서 정확한지는 여전히 검증하지 못했다.

## 4. 확인된 사항 (실제로 검증 완료)

### 로컬 시험
- **순수 계산 로직**: `src/lib/*.ts` 61개 vitest 테스트(날짜/도착일, 추천수량, 대기량, 참고값,
  회귀모델, 판매파일 파싱·행 분류·인코딩, CatPOS 파서, OCR 행 추출 등)가 모두 통과하며 설계
  문서의 숫자 예제를 그대로 재현한다.
- **DB 마이그레이션 0001~0010**을 로컬 PostgreSQL 스모크 테스트로 먼저 검증해 실제 버그 2건을
  찾아 고쳤다(RLS의 GRANT 누락, `confirm_order`의 발주 시각 처리).
- **판매 업로드 오류 처리(FR-06)**: 품목은 확인됐지만 날짜·수량이 깨진 행을 조용히 빠뜨리던
  문제를 고쳐, 이제는 저장을 막고 직접 수정하거나 명시적으로 제외해야 한다(21개 테스트).
- **CatPOS 표본 인코딩·날짜 버그 2건**: BOM 없는 UTF-8 CSV의 한글 깨짐, `cellDates:true`의
  로컬 시간대 해석으로 인한 날짜 하루 밀림 — 둘 다 실제 표본으로 재현·수정 확인했다.

### 실제 Supabase(`sotfjvjrtnnfgqsuxbgq`)·Cloudflare Pages 연동 시험 (이번에 새로 완료)
- **마이그레이션 0001~0010 전체를 실제 프로젝트에 `supabase db push`로 적용** — 오류 없음.
- **공개 가입 비활성화**(FR-01): `supabase/config.toml`로 `auth.enable_signup=false` 적용.
  최초 시도에서 `auth.email.enable_signup=false`도 함께 껐더니 **사전 발급 계정의 로그인까지
  막히는 실제 버그를 발견**했다(문서상 "신규 가입 허용 여부"이지만 실제로는 이메일 로그인
  자체의 스위치였다) — `true`로 되돌려 기존 계정 로그인은 열어 두고 공개 가입만 차단하도록
  고쳤다. 실제 로그인 화면에서 사전 발급 계정으로 로그인 성공을 확인했다.
- **Auth 리디렉션·CORS**(IR-11): `site_url`/`additional_redirect_urls`를 실제 Pages 주소로 설정.
- **Edge Functions 실제 배포·호출·정기 실행**: `holiday-sync`, `forecast-batch` 둘 다
  `supabase functions deploy`로 배포했다. 사용자가 공공데이터포털에 미리 로그인해 둔
  화면에서 한국천문연구원 특일 정보 API의 실제 서비스 키를 확인해(화면에서 값만 확인, 채팅에는
  입력받지 않음) `supabase secrets set`으로 등록한 뒤 `holiday-sync`를 실제로 호출했다 —
  2026·2027년 대체공휴일 포함 46건의 실제 공휴일 데이터를 정상적으로 받아와 `holiday_dates`에
  저장함을 DB로 직접 확인했다. `pg_cron`+`pg_net`으로 `holiday-sync`(매일 KST 02:00),
  `forecast-batch`(10분마다, 판매 업로드 직후 즉시 호출의 보조 수단) 정기 자동 실행도
  등록했다(`0011_edge_function_schedules.sql`).
- **계정 발급 스크립트 실행 중 실제 버그 발견·수정**: Node 20에는 전역 WebSocket이 없어(22부터
  기본 제공) `createClient`가 내부적으로 만드는 Realtime 클라이언트 초기화가 즉시 예외를
  던졌다 — `ws` 패키지를 명시적으로 넘기도록 고쳐 실제 서비스 키로 관리자 계정 발급에 성공했다.
- **전체 업무 흐름을 실제 REST API(Auth JWT + PostgREST + Edge Function)로 끝까지 확인**:
  180일치 합성 판매 데이터를 `begin_sales_import`→`stage_sales_rows`→`commit_sales_import`로
  업로드 → `forecast-batch` 호출로 회귀모델 학습(180 관측치)과 최근입고 기준 참고값 계산 →
  추천 생성(도착일 계산, 추천수량 66 = MOQ10·7일수요62·단위6의 FR-26 공식과 정확히 일치) →
  관리자 `confirm_order`로 발주 완료(대기량 66) → 부분 입고 33개(대기 33, 추천 상태 waiting
  유지) → 잔량 33개 입고(대기 0, 추천 상태 received로 종결)까지 전부 실제 값으로 확인했다.
  시험에 쓴 합성 품목·거래처·판매자료는 시험 후 전부 삭제했다.
- 로그인 화면은 브라우저로 실제 배포 주소에서 데스크톱·375px 모바일 모두 정상 렌더링을
  확인했다(이전 로컬 확인에 이어 실제 배포 환경에서도 재확인).
