# 직원의 자료 수집과 최종 판단을 지원하는 사입 추천 시스템

개발 사양서 v1.0 · 작성일 2026-09-23 · 언어 한국어 · 기준 시간대 Asia/Seoul

이 문서는 지금까지의 사용자 요구, 제공된 판매파일·입고장 사례 및 실행 중인 팜페이 플러스 앱의 화면 확인 결과를 바탕으로 작성했다. 제품의 구현 범위와 검수 기준을 정의하며, 실제 서비스가 구현되거나 배포되었다는 뜻은 아니다.

정책의 구분은 다음과 같다.

- **확정 요구**: 사용자가 제시한 업무 방식과 서비스 조건.
- **설계 기본안**: 개발을 진행하기 위해 이 문서가 정한 초기 동작. 설정으로 변경할 수 있어야 한다.
- **운영 전 확인**: 실제 발주 결과에 영향을 주므로 서비스 적용 전에 현장 또는 도매상과 확인할 항목. 17장에 모았다.

## 1. 제품 목적과 범위

직원이 POS에서 판매내역을 업로드하고 iPhone으로 종이 입고장을 등록하면, 시스템이 품목별 판매량·입고·실사·미입고 발주를 연결해 사입 후보와 구매수량을 제시한다. 재택 중인 발주 담당자(국장)는 PC 또는 Mac에서 근거를 검토하고 발주목록을 확정한 뒤, 기존 도매상 주문 채널에서 실제 주문한다.

초기 서비스는 한 약국의 여러 직원과 국장이 사용하는 구조로 제공한다. 여러 약국으로 확장할 때 자료가 섞이지 않도록 모든 업무 데이터에 약국 식별자를 둔다. 초기 버전에는 약국 간 재고 이동이나 통합 구매를 포함하지 않는다.

### 1.1 필수 서비스 조건

| ID | 확정 요구 | 구현 조건 |
|---|---|---|
| CORE-01 | 웹 표준을 준수하는 웹 서비스 | HTTPS 기반 반응형 웹. 별도 실행파일·브라우저 플러그인 설치 없이 핵심 업무 수행 |
| CORE-02 | Windows·macOS·iPhone 사용 | Windows 11의 Edge/Chrome, macOS의 Safari/Chrome, iPhone의 Safari에서 검수 |
| CORE-03 | 여러 기기에서 실시간 사용 | 중앙 서버와 데이터베이스에 저장하고 변경사항을 접속 중인 기기에 전파 |
| CORE-04 | 사전 발급 계정 로그인 | 공개 회원가입 없이 관리자가 발급한 개인별 계정만 사용 |
| CORE-05 | POS PC에서 판매내역 업로드 | 직원이 CatPOS Cloud에서 내보낸 파일을 웹 화면에서 업로드 |
| CORE-06 | 직원 iPhone에서 입고장 업로드 | 카메라 촬영 또는 사진 선택, 여러 장 묶음 업로드, 입고 검수 |
| CORE-07 | 국장 PC/Mac에서 발주 지원 | 추천 검토, 실사 요청, 도매상별 구매안 편집, 목록 확정·내보내기·실제 주문 기록 |

### 1.2 자동화 범위

시스템은 파일 해석, 입고장 문자 인식, 상품 매칭 후보 제시, 30일 판매 집계, 재고 추정, 사입 추천, 최소주문금액 계산, 상태 공유를 수행한다.

사람은 판매파일 내보내기·업로드, 입고장 촬영, 실제 도착 수량 확인, 필요한 재고 실사, 판독·매칭 오류 수정, 최종 구매 판단과 외부 주문을 수행한다. 정상적으로 인식되고 검증되는 항목은 묶음 확인할 수 있도록 하되, 오류가 있는 항목만 집중해서 처리할 수 있어야 한다.

초기 범위에서 제외하는 기능은 POS API 연동, POS·팜페이 앱 화면의 무인 반복 수집, 도매상에 대한 자동 주문·결제, 네이티브 iOS/Windows/macOS 앱, 오프라인 상태의 발주 확정, 머신러닝 수요예측이다. 이후 확장을 위한 데이터 구조는 유지한다.

## 2. 업무 근거와 입력 자료

### 2.1 확인된 업무 환경

- POS: Windows 11에서 운영되는 CatPOS Cloud(팜페이). 현재 알려진 연동 API는 없다.
- 판매내역: 직원이 하루 1회 내보내는 방식이 현재 가장 확실한 수집 경로다.
- 입고: 여러 배송업체가 하루 여러 차례 방문하며, 입고 시각은 06:00~20:00 사이에 불규칙하다. 종이 거래명세서가 배송물에 포함된다.
- 재고: 기존 재고 자료가 있지만 정확도를 보장할 수 없다. 입고 시 확인·실사를 기본으로 한다.
- 분석: 최근 30일 판매수량을 기준으로 하며 상위 50개 품목을 별도 관리한다.
- 사입: 기본적으로 MOQ를 구매한다. 가급적 일주일 판매분을 구매하는 것이 이상적이나, 목표 잔여재고 일수는 별도로 정하지 않았다.
- 발주 시점: 기본적으로 2일 판매분 정도 남으면 주문한다. 평일 오전 주문 시 다음 배송 영업일 도착을 전제로 하되, 주말·공휴일을 반영한다.
- 구매 제약: 프로모션, 도매상별 최소주문금액 때문에 추가 구매가 발생한다.

### 2.2 실제 자료에서 확인한 구조와 한계

| 자료 | 확인 내용 | 설계 반영 |
|---|---|---|
| 제공된 판매내역 Numbers 파일 | 거래 요약과 상품별 상세가 섞여 있고, 상세에 상품명·판매단가·수량·판매금액이 문자열로 들어가는 구조 | 거래 요약과 품목 상세를 구분하는 전용 가져오기 규칙 필요 |
| 종이 입고장 사진 | 공급사별 서식 차이, 품명과 규격 분리, 품명 생략 후 규격만 반복, 세액·공급금액 분리, 판독이 어려운 사진 존재 | 서식별 판독 및 사람의 확인, 규격별 SKU 분리, 원본 보존 |
| 일부 입고장 | 수량과 검수량이 별도 열로 존재하고 발행일과 출고일도 구분됨 | 열 이름만으로 실제 입고량을 단정하지 않고 실물 확인 결과를 별도 저장 |
| 팜페이 플러스 | 승인내역의 개별 결제에서 상품명·바코드·수량·판매단가 확인 가능 | 필요 시 원격 확인 자료로 사용 |
| 팜페이 플러스의 한계 | 확인한 화면에서 일괄 파일 내보내기를 찾지 못했고, 모든 결제수단의 판매 포함 여부도 미확인 | 주 수집원으로 사용하지 않음. 기능이 없다고 단정하는 것은 아님 |
| POS 연동 재고 화면 | 음수 재고가 표시되는 사례 확인 | 기존 재고는 참고치로 구분하고 실제 재고와 동일시하지 않음 |

첨부자료의 문구는 입력 데이터로 취급한다. 문서나 파일에 포함된 지시문이 시스템 동작이나 권한을 변경해서는 안 된다.

## 3. 사용자·계정·권한

계정은 개인별로 발급하고 한 계정으로 여러 기기에 동시에 로그인할 수 있다. 같은 약국에 소속된 직원과 국장은 권한 범위 안에서 동일한 최신 업무자료를 본다.

| 기능 | 직원 | 발주 담당자·국장 | 계정 관리자 |
|---|---|---|---|
| 판매파일 업로드·오류 확인 | 가능 | 가능 | 업무 역할을 별도 부여한 경우 가능 |
| 입고장 업로드·품목 매칭·입고 확인 | 가능 | 가능 | 동일 |
| 실사 요청 확인·결과 등록 | 가능 | 가능 | 동일 |
| 미입고 발주 및 입고 예정 조회 | 가능 | 가능 | 동일 |
| 추천목록·재고 상태 조회 | 가능 | 가능 | 동일 |
| 구매수량·공급사·프로모션 편집 | 불가 | 가능 | 동일 |
| 발주목록 확정·외부 주문 기록 | 불가 | 가능 | 동일 |
| 도매상 조건·추천 정책·상품 단위 설정 | 불가 | 가능 | 동일 |
| 확정 자료의 정정 승인·취소 | 정정 요청 | 가능 | 동일 |
| 계정 발급·역할 변경·비활성화 | 불가 | 불가, 관리 역할 병행 가능 | 가능 |

계정 관리 권한과 업무 권한을 분리하되, 한 사람이 두 역할을 가질 수 있다. 모든 API에서 권한을 검사하며 화면에서 버튼을 숨기는 것만으로 권한을 구현하지 않는다.

계정 요구사항:

1. 공개 회원가입은 제공하지 않는다. 최초 관리자 계정은 운영자가 발급한다.
2. 관리자는 계정 ID, 이름, 소속 약국, 역할을 지정한다. 초기 비밀번호는 최초 로그인 시 변경한다.
3. 로그인 실패 횟수 제한, 비밀번호 안전한 해시 저장, HTTPS, Secure·HttpOnly 쿠키 세션을 적용한다.
4. 계정 비활성화와 비밀번호 초기화 시 기존 세션을 폐기한다. 사용자는 자신의 접속 기기를 확인하고 로그아웃시킬 수 있다.
5. 권한 변경은 다음 요청부터 적용하며, 로그인 만료 시 입력 내용을 잃지 않도록 재로그인 후 재확인 절차를 제공한다.
6. 직원 공유계정을 기본 운영 방식으로 삼지 않는다. 업로드·수정·확정·주문의 담당자를 구분할 수 있어야 한다.

## 4. 기기별 업무 흐름

### 4.1 하루 운영 순서

| 순서 | 담당·기기 | 수행 내용 | 시스템 처리 |
|---|---|---|---|
| 1 | 직원·POS Windows PC | 하루 1회, 마감된 판매기간을 내보내고 업로드 | 중복·누락·형식·합계 검사 후 판매 반영 |
| 2 | 직원·iPhone | 배송마다 입고장 촬영, 실제 도착 수량 및 필요한 실사 결과 입력 | 판독·매칭·검수 후 입고·재고 반영 |
| 3 | 시스템 | 판매·입고·실사·주문 상태 변경 감지 | 관련 상품의 재고와 사입 후보 갱신 |
| 4 | 국장·PC 또는 Mac | 추천 근거와 자료 기준시점 확인, 필요 시 실사 요청 | 직원의 할 일에 실사 요청 표시 |
| 5 | 직원·iPhone | 요청된 품목 실사 | 국장 화면의 실사 상태와 추천 갱신 |
| 6 | 국장·PC 또는 Mac | 도매상·수량·MOQ·프로모션·최소금액 검토 | 구매안과 과잉·부족·자료오류 표시 |
| 7 | 국장·PC 또는 Mac | 발주목록 확정, 기존 주문 채널에서 실제 주문 | 실제 주문 기록 후 미입고 수량으로 관리 |
| 8 | 직원·iPhone | 이후 배송을 주문과 연결하여 확인 | 부분입고·완료·차이 관리 및 중복 추천 방지 |

입고 등록은 정해진 한 번의 마감 작업이 아니라 배송이 발생할 때마다 처리한다. 판매파일은 다음 오전 발주 전에 마지막 마감일까지 반영하는 운영을 기본안으로 한다. 구체적인 직원 업로드 시각은 현장 일정에 맞춰 설정한다.

국장은 재택에서 약국 PC의 원격 데스크톱에 접속하지 않고 서비스에 로그인해 업무를 수행한다. 서버 반영이 완료된 자료는 POS PC가 꺼져 있어도 조회할 수 있다.

### 4.2 대표적인 기기 간 연결

직원이 iPhone에서 입고장을 올리면 국장 화면에는 먼저 ‘판독 중’ 상태가 나타난다. 직원이 실제 입고량을 확인하고 확정하면 재고와 추천이 갱신된다. 판독 중인 문서를 확정 입고로 먼저 계산해서는 안 된다.

국장이 실사를 요청하면 직원의 할 일 목록에 품목과 요청 사유가 나타난다. 직원이 결과를 등록하면 국장은 새로고침 없이 확인할 수 있다. 화면을 닫았거나 휴대전화가 잠긴 경우에는 앱을 다시 열 때 최신 상태를 가져온다.

| 발주 기록 | 확정 목록, 실제 주문 여부·일시·담당자·주문번호, 도착예정일, 부분입고·미입고·취소 |
| 설정·관리 | 계정·권한, 상품 매핑, 거래처 조건, 배송 달력·마감시간, 분석 규칙, 활동·정정 이력 |

iPhone에서는 촬영·검수·실사 버튼을 우선 배치하고, 큰 표는 품목별 카드와 상세 화면으로 제공한다. PC/Mac에서는 표 정렬·필터, 다중 선택, 원본과 인식결과의 나란한 비교를 제공한다. 핵심 기능은 화면 크기 때문에 사용 불가능해져서는 안 된다.

## 6. 판매내역 수집·반영

### 6.1 파일 형식과 업로드

- 초기 필수 지원: `.xlsx`와 `.csv`. 파일을 읽는 기능과 실제 CatPOS 출력 구조를 해석하는 기능을 구분하며, 현장에서 사용하는 내보내기 형식으로 품목별 파서를 최종 검수한다. CSV 인코딩·구분자도 검증한다.
- `.xls`는 실제 POS 출력이 해당 형식일 경우 지원 범위에 포함한다. 운영 전에 원본 출력 형식을 확인한다.
- 제공된 `.numbers` 자료는 분석 참고자료다. 초기 서비스의 직접 입력은 Excel 또는 CSV로 내보낸 파일로 통일하는 설계 기본안이다. Numbers 파일 선택 시 변환 안내를 표시한다.
- 직원은 약국, 조회 시작·종료일, 데이터 마감시점을 확인한 후 업로드한다. 파일에서 읽을 수 있는 값은 자동 입력한다.
- 최근 30일의 마감된 판매를 매일 다시 내보내는 방식을 우선한다. POS 제약으로 일별 추출만 가능하면 마지막 반영 이후의 모든 날짜를 이어서 수집한다.
- 업로드, 해석, 검증, 반영 상태를 구분한다. 전송이 끝났다는 이유만으로 ‘판매 반영 완료’를 표시하지 않는다.

### 6.2 품목별 데이터 모델

최소한 판매일시 또는 판매일자, 원거래 식별자(있을 경우), 원행 식별자, 상품명, 규격·바코드(제공될 경우), 판매수량, 단가, 금액, 판매·반품·취소 구분을 저장한다. 원본 파일과 행 위치를 추적할 수 있어야 한다.

거래 요약의 ‘상품 A 외 1품목’은 SKU로 등록하지 않는다. 상품 상세행을 집계하고 거래 요약은 대조용으로 사용한다. 요약 금액과 상세 금액을 동시에 합산하지 않는다. 문자열 안에 구분기호가 포함된 상품명도 손상 없이 처리하도록 실제 내보내기 형식에 맞춘 해석 규칙을 둔다.

거래번호·바코드가 없는 형식도 받을 수 있지만, 누락 사실을 기록한다. 신규 형식이나 알 수 없는 열 배치에서는 임의 해석 후 반영하지 않고 미리보기·매핑 확인으로 전환한다.

### 6.3 중복·정정·누락 처리

1. 같은 파일 재업로드는 파일 해시로 식별하고 재반영하지 않는다.
2. 기간이 겹치는 다른 파일은 원거래 ID와 품목행 ID로 대조한다. 파일 해시만으로 거래 중복을 방지했다고 간주하지 않는다.
3. 안정적인 거래 ID가 없으면 동일 상품·시간·수량의 실제 별개 판매를 자동으로 합치지 않는다. 해당 내보내기가 기간 전체를 포함함이 확인된 경우에만 기간 단위 교체 방식을 사용한다.
4. 기간 교체는 누락·변경·추가 건수 미리보기, 담당자 확인, 원본 보존 후 하나의 트랜잭션으로 반영한다. 이전 자료는 삭제하지 않고 대체 이력을 남긴다.
5. 반품·취소는 품목 수량과 원거래 연결을 검증한다. 취소와 환불 기록이 함께 있다는 이유로 두 번 차감하지 않는다.
6. 금액 환불만으로 실물 재고 복귀를 추정하지 않는다. 재판매 가능한 실제 반품 입고가 확인될 때 재고에 더한다.
7. 파일의 전체 거래건수·합계와 해석 결과를 대조한다. 불일치나 미매칭 행이 남은 구간은 ‘완전 반영’ 상태가 될 수 없다.
8. 파일이 없는 날짜를 판매 0으로 처리하지 않는다. 실제 영업 없음 또는 매출 없음이 확인된 날짜만 사유·담당자와 함께 0으로 확정할 수 있다.

해석 성공행을 미리 저장할 수는 있으나, 검증에 실패한 배치를 조용히 일부 확정하지 않는다. 정상행을 먼저 반영하는 예외 기능이 필요하면 미해결행과 불완전한 기간이 추천 화면에 계속 표시되어야 한다.

### 6.4 판매 반영시점과 30일 창

최근 연속된 완전 반영일을 D라고 할 때 분석 기간은 D-29일부터 D일까지의 30개 달력일이다. 오늘 진행 중인 판매는 기본 순위·평균 집계에서 제외한다. 30일보다 적은 자료만 있으면 수집된 기간과 관측일 수를 표시하고 ‘30일 분석 준비 중’으로 분리한다.

기본 일평균 판매량은 해당 30일 순판매수량 ÷ 30이다. 영업하지 않은 날짜도 확인된 실제 0으로 포함된다. 누락일을 분모에 포함해 판매속도를 낮추지 않는다. 향후 영업일 기준 평균을 추가할 경우 계산 방식과 분모를 명시적으로 바꿔야 한다.

오래된 파일만으로 계산한 추천을 오늘의 완전한 결과처럼 표시하지 않는다. 마지막 완전 반영일, 미수집 기간, 부분반영 여부를 모든 추천 결과에 함께 표시한다.

## 7. 입고장 촬영·판독·검수

### 7.1 업로드

iPhone Safari에서 카메라 촬영과 기존 사진 선택을 모두 제공한다. 촬영 기능 사용이 불가능하거나 권한을 주지 않은 경우에도 사진·파일 선택으로 업로드할 수 있어야 한다. 표준 파일 입력의 `capture` 동작에만 의존하지 않는다. [MDN의 파일 입력 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file)

JPEG·PNG·HEIC를 필수 지원하며 서버에서 판독용 이미지로 변환한다. 초기 운영 한도는 이미지당 20MB, 문서당 10장으로 제안하며 설정으로 조정한다. PDF 업로드는 후속 확장으로 둔다. 원본은 유지하고 회전·기울기 보정 이미지는 별도로 만든다.

한 배송에 여러 장의 입고장이 있거나 한 입고장이 여러 페이지일 수 있다. 문서 묶음을 나누고 합칠 수 있어야 한다. 업로드 재시도는 같은 요청 ID를 사용하여 같은 사진이 여러 건의 입고로 생성되지 않도록 한다.

### 7.2 판독 필드

문서: 공급사, 명세서 번호, 발행일, 출고일, 실제 도착일시, 공급가액, 세액, 합계, 페이지 수.

품목: 원문 상품명, 규격, 상품코드·바코드(있을 경우), 청구수량, 수량 단위, 무상·증정 수량, 단가, 금액, 제조번호·유효기간(있을 경우).

실제 도착일시는 직원 입력을 기준으로 하며 최초값은 촬영 시각으로 제안한다. 발행일·출고일·촬영일을 실제 입고일로 자동 확정하지 않는다.

이전 행의 상품명이 생략된 서식은 이어쓰기 후보를 제시하되, 규격이 달라지면 별도 SKU로 처리한다. ‘1+1’ 표기만 보고 수량을 두 배로 계산하지 않는다. 직원이 실제 받은 판매단위 수량을 확인한다.

OCR 결과는 후보 자료다. 각 필드에 원본 위치와 확인 필요 여부를 연결하고, 합계 불일치·판독불가·신규 품목·단위 미확인 행을 강조한다. 외부 문자 인식 또는 AI 처리가 실패해도 수동으로 입력·확정할 수 있어야 한다.

### 7.3 상품 매칭

1. 바코드와 규격이 일치하는 기존 SKU를 우선한다.
2. 확정된 ‘공급사별 상품명·상품코드 ↔ 내부 SKU’ 매핑을 사용한다.
3. 그 외에는 정규화한 상품명·규격으로 후보를 제시한다. 유사 이름이라는 이유만으로 자동 확정하지 않는다.
4. 상품명은 같아도 함량·용량·포장규격이 다르면 별개 SKU다.
5. 직원이 확정한 별칭을 재사용하되 잘못된 매핑을 정정할 수 있어야 한다. 이미 반영된 재고의 재배정은 국장 승인과 이력을 필요로 한다.

### 7.4 실제 입고량과 실사를 분리

‘이번 택배에 들어 있는 수량 확인’과 ‘진열대·창고를 합친 전체 보유수량 실사’는 서로 다른 입력이다.

- 모든 입고에서는 실제 받은 수량을 확인한다. 명세서 수량과 다르면 차이와 사유를 남긴다.
- 저판매 품목의 전체 재고 실사가 필요한 경우 기존 재고까지 포함하여 입력한다.
- 실사값에 이번 입고가 포함되었는지 명시한다. 포함된 입고를 다시 더하지 않는다.
- 정상 수량과 파손·반품 예정 수량을 나누며, 판매 불가능한 수량은 가용재고에 넣지 않는다.
- 확정 전까지는 재고를 변경하지 않는다. 판독 또는 검수 중인 입고가 존재한다는 사실은 추천 화면에 표시한다.

### 7.5 입고 상태와 정정

상태는 `업로드 중 → 판독 대기 → 판독 중 → 검수 필요 → 확정`이며 실패 시 `처리 실패`와 재시도·수동 입력을 제공한다. 명확한 중복이나 잘못된 업로드는 확정 전에 취소할 수 있다.

확정 뒤 수량 정정은 기존 입고행을 지우는 방식이 아니라 반대 방향의 정정 기록과 올바른 기록을 남긴다. 관련 재고, 주문의 입고량, 추천을 함께 다시 계산한다.

동일 사진 해시와 공급사·문서번호·일자·금액 조합으로 중복 후보를 표시한다. 서로 다른 배송에서 같은 금액이 나왔다는 이유만으로 자동 삭제하지 않는다.

## 8. 재고 관리와 상위 50개 품목

### 8.1 상품·단위 기준

내부 SKU마다 하나의 판매 기준단위를 정한다. 예를 들어 ‘연고 20g 1개’와 ‘동일 제품 30g 1개’는 별개 SKU이며, 판매수량을 금액이나 포장 내부 낱개 수와 혼동하지 않는다.

입고 단위·발주 단위는 판매 기준단위로 환산할 수 있어야 한다. ‘1박스 = 판매단위 10개’와 같은 공급사별 환산계수를 둔다. 환산관계 미등록 상태에서는 입고수량을 임의로 판매단위 수량으로 계산하지 않는다.

### 8.2 재고 산식

```text
기록상 가용재고
  = 최근 신뢰할 수 있는 실사 기준재고
  + 그 기준 이후 확정된 정상 입고
  + 재판매 가능함이 확인된 반품 입고
  - 그 기준 이후 반영된 실제 판매 출고
  - 파손·폐기·공급사 반품 출고
  ± 승인된 재고 정정

현재 추정재고
  = 기록상 가용재고
  - 판매 미수집 구간의 예상 판매수량
```

입고 확정과 재고 실사에는 실제 발생시각과 시스템 기록시각을 모두 저장한다. 실제 발생시각과 실사에 포함된 사건을 기준으로 계산한다. 실사 이전 판매가 나중에 업로드되어도 실사값에서 다시 차감하지 않는다. 날짜만 있고 시각이 없는 자료가 실사 시점과 겹치면 마감시점 실사 또는 담당자의 포함범위 확인을 요구한다.

예상 판매는 장부에 실제 출고로 기록하지 않는다. 해당 구간의 실제 판매가 들어오면 예상분을 대체하고 새 기준으로 계산한다. 실제 판매와 예상 판매를 함께 빼지 않는다.

판매 통계의 취소·반품 처리와 실물 재고의 복귀는 분리한다. 예를 들어 출고 후 환불된 상품은 판매 통계에서 차감하더라도 실제 재입고 확인 전에는 재고가 늘지 않는다. 기존 출고를 되돌리는 정정과 별도 반품 입고가 같은 물량에 이중 적용되지 않도록 원거래·재고 이벤트를 연결한다.

‘마지막 입고수량 - 이후 판매량’만으로 전체 재고를 계산하지 않는다. 이전 잔량과 중간 추가 입고가 반영되어야 한다. 신뢰할 기준재고가 없으면 절대 재고수량은 미확정이며, 입고 이후 소진 추이는 참고정보로만 제공한다.

### 8.3 관리군

| 구분 | 분류 기준 | 기본 운영 |
|---|---|---|
| 상위 품목 | 최근 완전한 30일 순판매수량 순위 1~50위 | 최초 신뢰할 기준재고를 확보한 후 통계 중심으로 운영. 이상 징후가 있을 때 실사 |
| 일반·하위 품목 | 상위 50개에 들지 않은 판매 가능 SKU | 입고 시 전체 재고 확인을 기본으로 하고, 사입 검토 시 오래된 실사나 불확실한 재고는 재확인 |
| 관측 부족·신규 | 30일 이력 부족, 미매칭 또는 판매자료 불완전 | 일반·하위 관리 방식을 적용하며 잠정 지표임을 표시 |

상위 50개는 판매금액이 아닌 SKU별 판매수량으로 선정한다. 동률은 최근 판매일이 늦은 순, 그다음 내부 SKU ID 순으로 정해 재현 가능하게 한다. 판매수량이 양수인 SKU가 50개 미만이면 해당 수만 분류한다. 완전한 판매 배치 반영 후 순위를 갱신하고 군 변경 이력을 저장한다.

현재의 30일 분석에서 순판매수량은 해당 기간에 기록된 판매수량에서 해당 기간에 기록된 취소·반품수량을 중복 없이 차감한 값이다. 원거래가 기간 밖에 있는 반품도 별도 표시한다. 같은 기간의 총판매·취소·반품을 함께 확인할 수 있어야 하며, 반품 집중 때문에 순판매가 음수인 품목은 정상 수요예측에 사용하지 않는다.

군이 바뀌었다고 재고를 초기화하지 않는다. 상위 품목이어도 기준재고 없음, 음수 재고, 입고·판매 단위 오류, 장기간 미확정 입고 등 이상이 있으면 실사 요청 대상이다.

### 8.4 재고 신뢰 상태

- `실사 기준 확보`: 실사에 근거해 이후 확정된 흐름을 추적하는 상태. 현재값까지 모두 실측이라는 뜻은 아니다.
- `추정 포함`: 미업로드 판매 구간을 추정한 상태.
- `확인 필요`: 기준재고 없음, 음수, 자료 누락, 단위 미확인 등 계산을 신뢰하기 어려운 상태.

마지막 실사시각, 마지막 판매 마감시점, 미확정 입고, 미입고 발주를 숫자 옆에 표시한다. 음수 재고를 0으로 덮어 숨기지 않는다. 기존 POS 재고는 별도 참고값으로 가져올 수 있지만 실사 기준 확보 상태를 자동 부여하지 않는다.

## 9. 사입 추천 규칙

### 9.1 계산에 사용하는 값

```text
d = 최근 완전한 30일 순판매수량 / 30
S = 현재 추정 가용재고
T = 지금 검토한 주문이 실제 도착할 수 있는 가장 이른 일시
L = 현재부터 T까지 예상 판매가 발생하는 기간의 일수 환산값
기본 발주 검토 기준 = d × max(2, L)
```

30일 순판매가 0 이하이면 재고일수를 무한대 숫자로 표시하지 않고 ‘판매속도 산정 불가/판매 없음’으로 표시한다. 음수 순판매, 갑작스러운 급감, 품절로 인한 판매 부재는 확인 대상으로 둔다. 판매가 0인 품목을 자동 추가구매 후보로 올리지 않는다.

### 9.2 주문 시점

기본적으로 S가 2일분 이하이면 발주 검토 대상으로 선정한다. 주말·공휴일·마감시간 때문에 도착까지 더 오래 걸리면 그 기간을 커버해야 하는지 함께 판단한다.

미입고 주문은 도착예정일별로 반영한 시간순 재고 예측에 사용한다. 향후 입고 예정이라는 이유만으로 현재 실물 재고에 더하지 않는다. 이미 주문된 수량이 필요한 시점의 부족을 해소하면 ‘발주됨·입고 대기’로 표시하고 중복 사입 후보에서 제외한다. 도착예정일이 없거나 지연된 주문은 확정된 공급으로 간주하지 않는다.

도착 전 품절이 예상되면 긴급 확인 대상으로 표시한다. 구매수량만 늘리면 도착 전 공백이 해결되는 것처럼 표시해서는 안 된다. 국장이 공급사 변경·긴급조달·보류를 판단한다.

### 9.3 배송 달력

- 공급사 업무일과 배송일의 기본값은 월~금이며 공휴일·개별 휴무를 제외한다.
- 오전 마감 이전 주문은 다음 배송 영업일 도착을 기본 규칙으로 둔다.
- 마감 이후 주문은 다음 주문 영업일 접수 후 그다음 배송 영업일 도착으로 계산하는 설계 기본안이다.
- 정확한 오전 마감시간은 거래처별로 설정한다. 미설정일 때 시간 단위의 확정 도착예측을 제시하지 않는다.
- 주말 배송이 없다는 사실과 약국의 주말 판매 여부는 분리한다. 약국이 영업하는 날의 판매를 예측에서 빼지 않는다.
- 휴일 달력은 관리자가 등록·수정할 수 있어야 하며 공급사별 예외 배송일·지연을 반영한다. 휴일 데이터의 적용 연도를 표시한다.

예: 별도 휴일이 없다면 금요일 오전 주문의 기본 도착일은 월요일이다. 월요일이 배송 휴무면 화요일이다. 이 기간에 약국이 영업하면 해당 판매를 고려한다.

### 9.4 구매수량: 최소안과 7일구매안

사용자는 고정 목표재고 일수를 설정하지 않았다. 따라서 ‘구매 후 재고를 항상 7일치로 맞춘다’는 규칙을 사용하지 않는다. 일주일은 구매량을 비교하는 기준이다.

| 구매안 | 계산과 의미 | 기본 동작 |
|---|---|---|
| 최소구매안 | 도매상·품목의 MOQ와 주문 가능한 단위 조건을 만족하는 가장 작은 양수 수량 | 기본 선택. 구매 후 예상 소진일과 다음 발주 필요시점을 함께 표시 |
| 7일구매안 | 약 7일 판매량을 새로 구매하는 수량을 MOQ·발주단위에 맞춰 올림 | 비교 선택지. 고정 목표재고 정책으로 취급하지 않음 |
| 담당자 조정안 | 국장이 정한 수량에 단위·MOQ·중복 주문·금액 조건을 검증 | 사유와 이전 추천값 저장 |

기본 선택을 최소구매안으로 하는 것은 ‘기본적으로 MOQ, 가능한 최소 구매’ 요구를 우선한 설계 기본안이다. 일주일분을 기본 선택으로 바꾸려면 운영 정책에서 명시적으로 변경한다.

MOQ가 m, 주문수량이 반드시 b의 배수인 경우:

```text
Qmin = b × ceil(m / b)
Q7   = b × ceil(max(m, 7 × d) / b)
```

일부 거래처가 ‘최초 MOQ + 추가 단위’ 규칙을 사용하면 `m + k×b` 형태의 별도 주문 가능 수량 규칙으로 계산한다. 어떤 방식인지 저장하고 섞어 쓰지 않는다. 계산은 모두 판매 기준단위로 한 뒤 실제 발주단위로 표시한다.

예: 일평균 3개, MOQ 10개, 5개 단위 주문이면 최소안 10개, 7일구매안 25개다. 현재 재고 5개를 21개에서 빼서 16개를 구매하도록 자동 결정하는 방식은 아니다.

품목별 MOQ·발주단위의 전수 사전 등록을 요구하지 않는다. 사입 후보가 되었을 때 국장이 확인해 저장할 수 있다. 미등록 상태에서는 7일 판매량 등의 참고수량만 표시하고 ‘거래처 조건 확인 필요’로 둔다. MOQ를 임의로 1로 가정하지 않으며, 과거 구매수량을 MOQ로 자동 확정하지 않는다.

### 9.5 도매상 최소주문금액

확정된 업무 기본값은 의약외품 50,000원, 의약품 200,000원이며 도매상별 설정이 우선한다. ‘일반의약품(OTC)’을 ‘의약외품’으로 분류하지 않는다. 기타 상품은 별도 조건으로 등록한다.

설정에는 최소금액, 적용 상품군, 같은 주문의 혼합 합산 허용 여부, 부가세 포함 여부, 할인 전후 기준, 배송비 포함 여부, 적용기간을 둔다. 미확인 조건은 미확인으로 표시하고 기본 금액만으로 조건 충족을 단정하지 않는다.

부족분을 채우는 후보는 판매가 많은 품목, 규격·단위·가격이 확인된 품목, 유효기간과 보관상 문제가 확인되지 않은 품목 중에서 선정한다. 기존 재고가 넉넉한 경우도 후보가 될 수 있으나 ‘최소금액 충족용 추가구매’로 분리하고 구매 후 재고일수와 추가금액을 표시한다.

추가구매 품목·수량은 국장이 선택한다. 시스템이 자동으로 발주목록에 확정하지 않는다. 모든 상품 조합에 대해 수학적으로 전역 최소금액을 보장하는 최적화는 초기 범위에 포함하지 않으며, 제안 결과를 ‘최적해 보장’으로 표현하지 않는다.

### 9.6 프로모션

수량별 할인, 금액별 할인, 무상 증정, 묶음 구매를 등록할 수 있어야 한다. 적용 공급사·상품·기간·조건·할인·증정량을 저장한다. 사람이 확인하지 않은 입고장 문구를 프로모션 규칙으로 자동 적용하지 않는다.

일반 구매안과 프로모션 구매안을 비교해 실제 지출액, 유상·무상 입고량, 판매단위당 실질 매입가, 구매 후 재고일수를 보여준다. 할인율만으로 과다 구매를 추천하지 않는다. 유효기간을 모르면 ‘미확인’으로 표시한다.

### 9.7 추천의 설명과 보류 조건

추천마다 분석 기간, 30일 판매량, 일평균, 기준·추정 재고, 실사·판매 기준시각, 예상 도착일, 미입고 주문, MOQ·발주단위, 단가 기준일, 추천 이유, 계산 버전을 표시한다.

기준재고 없음, 상품 매칭 실패, 단위 미확인, 누락 판매, 미확정 관련 입고, 오래된 단가 등은 각각 구체적인 해결 작업으로 연결한다. 계산 불능 항목은 정상 추천 수량으로 표시하지 않는다. 국장은 자료 확인이 어려워도 수동 판단으로 주문할 수 있지만, 미해결 상태와 판단 사유를 기록해야 한다.

## 10. 발주목록·실제 주문·입고 연결

발주 상태는 `작성 중 → 검토 완료 → 목록 확정 → 실제 주문 완료 → 부분입고 → 입고 완료`를 기본으로 한다. 외부 주문 이전에는 취소할 수 있고, 실제 주문 이후 취소는 거래처와 취소 사실을 확인해 기록한다.

‘목록 확정’, 파일 다운로드, 인쇄만으로 실제 주문 완료가 되지 않는다. 국장이 기존 도매상 웹사이트·전화 등에서 주문한 다음 주문일시, 담당자, 거래처 주문번호(있는 경우), 도착예정일을 입력해야 미입고 발주로 계산한다.

발주목록은 공급사별 Excel·CSV 내보내기와 브라우저 인쇄를 지원한다. 품목명·규격·거래처 코드·주문단위·수량·예상금액을 포함한다. 외부 주문 채널의 입력 형식을 특정하지 않은 초기 버전에서는 범용 목록을 제공한다.

같은 추천을 두 사람이 동시에 주문 처리하지 않도록 주문 상태 전환에 버전 검사를 적용한다. 동시에 열린 구매안이 있으면 담당자와 상태를 표시한다. 한 명이 주문을 기록하면 다른 사람의 오래된 확정 시도는 차이를 확인한 뒤 재검토하게 한다.

한 발주가 여러 배송으로 나뉘거나, 한 입고장이 여러 발주에 걸칠 수 있으므로 발주행과 입고행을 수량 단위로 연결한다. 초과·부족·대체품·파손은 차이로 남기고 자동 완료시키지 않는다. 발주 연결은 이미 발생한 입고를 재고에 또 추가하지 않는다.

## 11. 실시간 공유·동시 편집·연결 끊김

이 서비스의 실시간은 서버에 저장·확정된 자료와 처리 상태의 즉시 공유를 뜻한다. POS에서 아직 내보내지 않은 판매, 직원이 아직 촬영하지 않은 종이 입고장은 시스템이 자동으로 알 수 없다.

실시간 공유 대상은 업로드·판독 상태, 판매 반영 완료, 입고 확정, 실사 요청·결과, 추천 갱신, 구매안 변경, 실제 주문·부분입고 상태다.

### 11.1 반영 순서와 충돌

1. 서버에서 검증과 저장을 완료한 뒤 변경 알림을 전송한다.
2. 다른 기기는 알림을 받고 해당 데이터의 최신 버전을 조회한다.
3. 수정 API는 대상 데이터 버전을 확인한다. 버전이 바뀌었으면 조용히 덮어쓰지 않고 변경 차이를 보여준다.
4. 추천에 영향을 주는 자료가 바뀌면 ‘다시 계산 중’을 표시한다. 오래된 추천을 새 결과처럼 유지하지 않는다.
5. 발주목록 확정 시 판매·입고·실사·미입고 주문의 기준 버전을 다시 검사한다. 변경이 있으면 변경된 품목을 재검토한다.

### 11.2 구현 기본안

입력·수정은 HTTPS API로 처리하고 서버 변경 알림은 SSE를 우선 사용한다. SSE는 서버에서 브라우저로 알림을 보내는 방식이므로 클라이언트의 수정 요청은 별도 API로 보낸다. [MDN의 SSE 설명](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

연결 복구 시 마지막 수신 이벤트 이후의 변경을 재조회하며, 이벤트 보존 구간을 벗어나면 화면 데이터를 전체 재조회한다. 이벤트의 전달 횟수에 의존하지 않고 고유 이벤트 ID·데이터 버전으로 중복·역순을 처리한다. SSE 사용이 어려운 환경에서는 주기적 재조회로 전환하고 지연 상태를 표시한다.

iPhone이 잠기거나 브라우저가 백그라운드로 이동한 상태의 지속 연결은 보장하지 않는다. 화면 복귀 시 최신 데이터를 확인하고 오래된 값으로 확정하지 않는다. 초기 버전의 알림은 웹 화면 내 알림이며, 앱을 닫은 상태의 푸시 알림은 별도 확장이다.

### 11.3 통신 실패

서버 응답을 받지 못하면 ‘성공’으로 표시하지 않는다. 재시도 시 요청 ID를 재사용해 입고·실사·주문이 중복 생성되지 않도록 한다. 전송 중 이탈에는 상태 안내를 제공한다. 완료하지 못한 사진은 재선택이 필요할 수 있음을 명시하고, iPhone 백그라운드 전송 완료를 보장하지 않는다.

오프라인에서는 마지막 조회시점과 연결 끊김을 표시한다. 서버 검증이 필요한 입고 확정·주문 완료는 온라인 복구 후 수행한다. 핵심 업무자료를 브라우저 LocalStorage에만 보관하지 않는다.

## 12. 시스템 구조와 데이터 설계

### 12.1 구성 기본안

반응형 웹 프런트엔드, 인증·업무 API 서버, 관계형 데이터베이스, 비공개 원본 파일 저장소, 비동기 작업 처리기, 실시간 알림으로 구성한다. POS가 설치된 PC는 파일 업로드 기기이며 서버 역할을 맡지 않는다.

관계형 데이터베이스는 PostgreSQL을 기본안으로 한다. 웹 구현 언어·프레임워크·호스팅 업체·OCR 공급자는 구현 착수 시 선택하며, 특정 버전이나 업체에 대한 종속을 제품 필수조건으로 두지 않는다. OCR 결과를 표준 필드로 변환하는 경계를 두어 공급자를 교체할 수 있게 한다.

긴 파일 해석·OCR·추천 계산은 작업 큐로 처리한다. 사용자 요청은 작업 ID를 반환하고 진행 상태를 조회할 수 있게 한다. 작업 재시도에도 같은 자료가 중복 반영되지 않아야 한다. 데이터 저장과 변경 알림 생성의 누락을 방지하도록 트랜잭션 내 변경 이벤트 기록 방식을 사용한다.

설계 지원 범위는 출시 검수 시점의 최신 안정판과 직전 주요 버전이다. 실제 검수한 OS·브라우저 버전은 검수표에 기록한다. 브라우저 에뮬레이션만으로 iPhone 지원을 검수 완료하지 않는다.

## 14. 보안·운영·성능 요구

### 14.1 자료와 접근

약국별 데이터 접근을 서버에서 제한하고 원본 파일은 공개 URL로 노출하지 않는다. 파일 조회 링크는 권한 확인 후 제한된 시간 동안만 사용할 수 있게 한다. 업로드 확장자뿐 아니라 실제 형식·크기·내용을 서버에서 검사한다. 판독 문서의 텍스트를 프로그램 명령이나 권한 지시로 실행하지 않는다.

필요한 판매 품목·수량·시간·금액을 중심으로 처리한다. 고객 이름·카드번호·승인번호 등 사입 계산에 불필요한 정보는 일반 업무 화면과 로그에 노출하지 않는다. 원본에 포함된 경우 원본 조회권한으로 제한하며, 외부 OCR 전송에는 필요한 입고장 이미지만 사용한다.

로그인, 업로드, 확정, 정정, 실사, 권한 변경, 실제 주문 기록은 행위자·시각·대상을 남긴다. 직원의 파일 삭제만으로 이미 확정된 업무 이력이 사라져서는 안 된다.

### 14.2 운영 기본안

- 업무 사용시간 목표 가용성: 월 99.5% 이상. 계획 점검은 업무시간을 피해 사전 안내한다.
- 데이터베이스 복구 목표: RPO 1시간 이내, RTO 4시간 이내를 기본안으로 하고 이를 충족하는 백업·복구 구성을 선택한다.
- 파일 저장소에는 버전 관리 또는 동등한 복구 수단을 적용한다. 데이터베이스와 원본 파일의 연결을 복구 점검에 포함한다.
- 백업은 30일 순환 보관을 기본안으로 한다. 원본·업무자료 자체의 보유기간은 별도 운영 정책으로 정하며, 정책 확정 전 자동 영구 삭제를 구현하지 않는다.
- 업로드·OCR·파서 실패, 장시간 미완료 작업, 실시간 연결 실패, 판매자료 누락을 운영 화면에서 확인할 수 있어야 한다.

위 수치는 개발·운영 비용 산정을 위한 제안 기준이며 실제 호스팅 계획과 함께 확정한다. 보유기간은 법정 보관기간을 이 문서에서 단정한 것이 아니다.

### 14.3 성능 검수 기본 부하

초기 검수 데이터는 SKU 10,000개, 최근 30일 판매 품목행 100,000개, 동시 접속 10명, 판매파일 최대 20MB를 기본으로 한다. 실제 운영량이 이를 넘으면 시험 부하를 조정한다.

| AT-10 | 과거 판매 지연 업로드와 실사 | 실사 이전 판매를 새 기준재고에서 재차 차감하지 않음 |

| AT-12 | 상위 50개·동률·신규 SKU | 판매수량 기준 및 동률 규칙이 재현되며 군 변경에도 재고 유지 |
| AT-13 | MOQ·발주단위·7일구매안 | 최소안과 7일안이 정의대로 계산되고 MOQ 미등록을 1로 가정하지 않음 |
| AT-14 | 금요일·공휴일·주문 마감 이후 | 배송 영업일을 적용하고 약국 영업일의 예상 판매는 반영 |
| AT-15 | 최소금액·혼합상품·프로모션 | 의약품/의약외품 구분, 합산·세금 기준, 증정 수량이 정확하고 추가구매는 담당자 선택 |
| AT-16 | 미입고 주문·지연·부분입고 | 실물 재고와 구분하며 적시 도착 수량만 중복 추천 방지에 사용 |
| AT-17 | 두 국장 화면의 동시 수정·주문 | 오래된 버전 덮어쓰기와 이중 주문 상태 생성 방지 |
| AT-18 | 판매자료가 바뀐 뒤 발주목록 확정 | 변경된 추천 근거를 보여주고 재검토 후 확정 |
| AT-19 | iPhone 잠금·네트워크 끊김·복귀 | 성공 오표시·중복 반영 없음, 최신 상태 재조회 |
| AT-20 | 다른 약국 ID·역할로 자료 접근 시도 | UI와 API 모두 권한 밖 자료 접근 차단 |
| AT-21 | OCR 서비스 실패 | 수동 입력으로 업무 지속, 실패 원인·재시도 상태 표시 |
| AT-22 | 백업 복구 | 계정·원장·주문·원본 연결이 복원되고 합계·잔량 일치 |
| AT-23 | 실제 기기·접근성·성능 | 지정 브라우저와 실제 iPhone에서 핵심 흐름 통과, 목표 부하 결과 기록 |

출시 전에는 실제 업무 표본으로 기존 수기 판단과 추천을 대조한다. 특히 단위 환산, 기준재고, 미입고 발주가 맞는지 확인해야 한다. 수치가 일치하지 않는 경우 원인을 해결한 뒤 해당 기능을 정상 추천으로 노출한다.

## 16. 개발 단계와 산출물

| 단계 | 구현 범위 | 완료 산출물 |
|---|---|---|
| 1. 업무·입력 규격 확정 | POS 원본 출력 형식·거래 키·기간 완전성, SKU 단위, 권한·도매상 정책 확인 | 입력 데이터 사전, 화면 흐름, 미확정 정책 목록 |
| 2. 공유 기반 | 계정·권한, 중앙 저장소, 파일 업로드, 상태 알림, 감사 이력 | 세 기기에서 로그인·업로드·상태 공유 가능한 서비스 |
| 3. 판매·입고·실사 | 전용 파서, OCR·수동 검수, 매칭, 재고 원장, 초기 기준재고 | 실제 표본으로 검증된 데이터 반영과 재고 이력 |
| 4. 추천·발주 | 30일 분석·상위 50개, 배송 달력, MOQ·최소금액·프로모션, 구매안·미입고 연결 | 설명 가능한 추천과 국장 발주 업무 전체 흐름 |
| 5. 운영 검수·출시 | 실제 iPhone·PC·Mac, 충돌·실패·복구·권한·성능 시험 | 검수표, 배포·복구 문서, 직원·국장 사용 안내 |

최종 개발 납품에는 소스코드, 실행·배포 설정, 데이터베이스 마이그레이션, API 명세, 파서·추천 계산 검증 자료, 실기기 검수 결과, 백업·복구 절차를 포함한다. 개발 기간과 비용은 구현 기술·OCR·호스팅 선택 후 산정하며 이 문서에서 확정하지 않는다.

기존 공개 저장소의 단일 페이지·브라우저 로컬 저장 기반 구현은 화면과 계산 아이디어의 참고로 사용할 수 있다. 본 요구를 충족하려면 계정·중앙 저장·실시간 공유·서버 검증을 갖춘 구조가 필요하며, 기존 코드가 이를 충족한다고 전제하지 않는다.

## 17. 운영 전 확인할 항목

아래는 개발 전체를 중단시키는 질문 목록이 아니다. 확정된 기능은 구현할 수 있으며, 해당 항목은 실제 계산·발주 적용 전에 확인하고 설정한다.

| 항목 | 확인 필요 내용 | 확인 전 처리 |
|---|---|---|
| 실제 POS 원본 파일 | xlsx/xls/csv, 모든 결제수단 포함, 거래·품목행 ID, 취소·반품 구조 | 제공 표본으로 파서 초안 개발, 실제 내보낸 파일로 최종 검수 |
| 판매자료 마감 | 하루 업로드 시각, POS의 일자 경계, 주말·휴일 약국 영업 | 마지막 완전 반영기간을 명시하고 누락은 미확정 |
| MOQ·발주단위 | 품목·공급사별 값, MOQ 이후 증가 방식, 박스 환산 | 후보가 될 때 필요한 품목부터 등록 |
| 도매상 최소금액 | 기본 5만원·20만원의 적용 범위, 혼합합산, 세금·할인·배송비 기준 | 기본 금액을 제시하되 조건 충족 여부는 확인 필요 |
| 배송 마감시간 | ‘오전’의 정확한 시각, 공휴일·특별휴무·예외 배송 | 날짜 수준 참고 예측, 확정 배송시각은 표시하지 않음 |
| 초기 재고 기준 | 상위 50개 우선 실사, 하위 품목 최초 확인 방식 | 미실사 품목의 절대 재고와 정상 추천 수량은 미확정 |
| 실사 유효성 | 하위 품목의 실사 재요청 기준·주기 | 최근 실사시각·이후 자료 완전성 표시, 국장 수동 요청 가능 |
| 입력자료 신선도 | 미업로드가 어느 정도면 발주 검토를 보류할지 | 미수집 구간을 항상 표시, 국장 예외 판단은 사유 기록 |
| 수량 기본 선택 | 최소구매안 우선 정책 유지 여부 | 본 문서 기본안은 최소구매안, 7일구매안은 비교 선택 |
| 서비스 운영 | 호스팅·OCR 공급자, 원본 보유기간, 복구 목표·지원 담당 | 운영 환경 배포 전에 설정·검수 |

## 18. 설계 근거 자료

- 사용자 제공 업무 조건 및 본 대화에서 합의된 서비스 방향.
- 사용자 제공 2026년 8월 판매내역 Numbers 파일과 5종 입고장 이미지. 원본 내용·계정정보를 공개 자료로 재배포하지 않는다.
- 실행 중인 팜페이 플러스의 승인내역·상품정보·상품관리·통계·재고 화면 확인 결과. 화면에서 확인하지 못한 API나 내보내기 기능의 존재 여부를 단정하지 않는다.
- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/): 접근성 목표의 기준.
- [MDN 파일 입력](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file): 브라우저 파일 선택·촬영 입력 설계 참고.
- [MDN Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events): 기기 간 서버 변경 알림 설계 참고.
