# 사입 추천 시스템 소프트웨어 요구사항 명세서

버전 1.0 · 작성일 2026-09-23

기준 문서: `사입추천시스템_개발작업지시서.md` — GitHub 원문 blob `69e6233d63408e8d2b71148484e1860f1a425d6c`.

이 명세서는 직원 약 5명이 판매·입고 자료를 등록하고 관리자가 사입 추천을 확인해 직접 발주하는 웹 서비스를 대상으로 한다. 기능적 요구사항은 `FR`, 비기능적 요구사항은 `NFR`, 인터페이스 요구사항은 `IR`로 식별한다. 번호는 개발·검수에서 요구사항을 찾기 위한 것이며, 현장 직원에게 추가 절차를 요구하지 않는다.

## 1. 작업지시서 검토 결과와 적용 범위

확정된 방향은 관리자/직원 두 권한, 마스터 또는 백엔드 개발자의 계정 발급, POS 일별 판매 집계, 기기 내 OCR과 사진 미전송, 180일 회귀분석, 주문 다음 날부터 2영업일 도착, MOQ와 도착 후 7일 판매량을 비교한 수량 추천, 사입 검토·입고 대기·입고 반영의 세 상태다. GitHub Pages와 Supabase 무료 플랜으로 운영하며 별도 DB 백업을 두지 않는다. 장애 시 수동 발주로 업무를 이어가고 프로젝트 재개 방법은 백엔드 개발 시 문서화한다.

검토 중 발견한 모호함과 처리 방향은 다음과 같다.

| 검토 사항 | 명세에서의 처리 |
|---|---|
| 일별 판매만으로 입고·실사 시각 이후 판매량을 정확히 구분할 수 없음 | 판매자료의 기준일을 표시한다. 입고 당일 차감과 장중 실사의 일별 환산은 아래 결정 항목 D-01로 분리한다. |
| MOQ·입고·판매의 박스/낱개 단위가 다를 수 있음 | 품목별 기준 단위와 환산값을 두고 계산 전에 같은 단위로 맞춘다. |
| 발주 건 연결 없이 부분 입고와 여러 번의 발주를 처리해야 함 | 품목별 입고 대기 총량을 갱신한다. 개별 주문의 배송 완료를 단정하지 않는다. |
| 180일이 지난 판매 삭제가 오래된 기준점 계산을 깨뜨릴 수 있음 | 과거 판매 누적값과 기준점을 남기고 일별 행만 정리한다. |
| 웹 앱은 사용자의 사진 보관함 원본을 임의로 삭제할 수 없음 | 앱이 보유한 임시 이미지 데이터만 삭제 대상으로 정의한다. |
| 회귀식·성능 기준·POS 열 구조가 확정되지 않음 | 구현 전 검증 항목으로 명시한다. 임의 구현을 확정 사양으로 간주하지 않는다. |

실제 주문은 기존 도매상 채널에서 사람이 한다. POS 자동 접속, 거래처 주문 전송, 택배 추적, 회계 정산은 이번 범위에 포함하지 않는다.

디자인 참고자료는 사용자가 제공한 `Bloomberg Terminal Clone` README다. 적용할 철학은 **판단에 필요한 정보를 한 화면에서 빠르게 비교하고, 자료 변경을 즉시 확인하는 업무용 터미널**이다. 관리자 PC는 표 중심의 높은 정보 밀도와 키보드 조작을, 직원 iPhone은 촬영·품목·수량 입력을 중심으로 구성한다. 참고자료의 미리보기 이미지와 실제 코드는 이번 검토에 제공되지 않았으므로 특정 화면을 복제하는 명세는 아니다. README의 기술 스택·설치 명령·금융 API·시뮬레이션 데이터는 제품 요구사항으로 가져오지 않는다.

## 2. 기능적 요구사항

### 계정과 권한

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| FR-01 | 사전 발급 계정으로 로그인·로그아웃한다. 공개 회원가입은 인증 서비스 설정에서도 비활성화한다. | 미발급 계정은 로그인할 수 없고 공개 가입 요청도 거부된다. |
| FR-02 | 마스터 또는 백엔드 개발자가 운영 도구에서 계정을 발급·비활성화하고 초기 비밀번호·재설정을 처리한다. 마스터는 운영 권한이며 앱의 세 번째 업무 역할을 만들지 않는다. | 일반 관리자·직원 화면에 계정 발급 기능이 없다. |
| FR-03 | 직원은 판매 업로드, 입고·실사 등록/정정, 품목 기본정보 등록(품명·규격·기준 단위·별칭·POS 코드·바코드)·검색 및 관련 내역 조회를 할 수 있다. 관리자는 같은 기능에 더해 MOQ·발주 단위·거래처 조건·휴무 설정과 추천 검토·발주 등록/정정을 할 수 있다. | 직원이 발주 확정·역할 변경·MOQ/발주단위 등 설정 변경 API를 직접 호출해도 거부된다. |
| FR-04 | 비활성 계정은 기존 세션이 남아 있어도 이후 업무 데이터 요청을 처리할 수 없게 한다. | 비활성화 후 읽기·쓰기 요청이 서버에서 거부된다. |

### 판매자료

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| FR-05 | 직원이 CatPOS 판매 파일을 업로드하면 날짜·품목별 순판매수량으로 집계한다. 판매일은 POS 값을 그대로 쓴다. | 같은 품목·날짜의 여러 행이 합산되고 판매 시·분·초는 분석 테이블에 없다. |
| FR-06 | 업로드 전/결과 화면에 자료 기간, 인식한 품목 수, 오류 행을 보여준다. 해석할 수 없는 날짜·수량·품목이 있으면 확정 저장 전에 수정할 수 있게 한다. | 잘못된 행을 임의의 날짜·수량으로 바꾸거나 조용히 누락하지 않는다. |
| FR-07 | 같은 파일 재전송은 중복 적용하지 않는다. 기간이 겹치는 파일도 품목·날짜 집계를 단순 누적하지 않는다. | 동일 파일을 두 번 올려도 판매량은 한 번 올렸을 때와 같다. 전체 기간 보고서는 해당 기간의 검증된 집계를 교체하며 교체 사실을 알린다. 증분 형식은 실제 POS 표본에서 식별자를 확인한 뒤 지원한다. |
| FR-08 | 자료가 정상적으로 포괄하는 날짜에 특정 품목 판매가 없으면 0으로 취급한다. 미업로드 날짜, 품목 취급 시작 전 기간은 확인된 0 판매와 구분한다. | 미업로드 날짜를 0으로 채워 수요가 낮아지지 않는다. 0 행은 DB에 모두 저장하지 않고 계산 시 생성해도 된다. |
| FR-09 | 반품·취소를 POS 정의에 맞게 반영하고 정정 업로드 시 판매 집계와 관련 추천을 다시 계산한다. | 양수 판매와 반품 부호를 실제 파일 표본으로 대조한다. 음수 순판매와 음수 예측값을 구분한다. |
| FR-10 | 최근 30일 순판매수량으로 품목 순위를 계산해 상위 50개를 통계 중심 관리 대상으로 표시한다. 나머지는 실사 중심으로 표시한다. | 동일 합계의 순위는 품목 ID 등 고정 기준으로 정렬하며, 자료가 부족하면 기간을 함께 표시한다. |

### 입고와 실사

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| FR-11 | iPhone에서 촬영 또는 사진 선택 후 기기 내 OCR을 실행하고 품목·규격·수량 후보를 표시한다. 직원이 수정·확정한 품목과 수량만 입고로 저장한다. | 사진·OCR 전체 원문이 서버 요청이나 로그에 포함되지 않는다. 불확실한 후보는 자동 확정하지 않는다. |
| FR-12 | OCR을 사용할 수 없거나 결과가 불완전해도 품목 검색과 수량 직접 입력으로 입고를 등록할 수 있다. | 카메라 권한을 거부해도 수동 입고가 가능하다. |
| FR-13 | 직원의 필수 입력은 품목과 실제 입고 수량이다. 건 ID·등록자·등록 시각은 자동으로 붙이고 실제 입고일/시각은 필요 시 수정한다. 한 번에 여러 품목, 하루 여러 입고를 지원한다. | 재전송·더블클릭이 같은 입고를 두 번 만들지 않는다. |
| FR-14 | 입고 수량은 기준 단위로 환산해 반영한다. 입고 등록과 정정은 재고 참고값·입고 대기량·추천에 반영한다. | 박스당 10개인 품목의 2박스 입고는 기준 단위 20개로 계산된다. |
| FR-15 | 실사는 특정 품목의 총 보유 수량을 입력하는 한 번의 작업으로 제공한다. 실사 기준점을 갱신하고 이미 포함된 입고를 다시 더하지 않는다. | 실사에 포함된 입고를 이중 계산하지 않는다. 장중 판매의 경계는 D-01을 적용한다. |

### 품목·거래처·공휴일

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| FR-16 | 표준 품목 ID, 품명, 규격, 기준 단위, POS 코드·바코드·별칭을 관리한다. 같은 이름이라도 규격이 다르면 별도 품목으로 구분한다. 직원·관리자 모두 품목 기본정보(품명·규격·기준 단위·별칭·POS 코드·바코드)를 등록할 수 있다. 등록 전 비슷한 기존 품목을 보여줘 중복 등록을 줄인다. 미등록 상태에서도 품목·입고를 저장할 수 있다. | 모호한 별칭이 여러 품목에 대응하면 사용자가 선택한다. 같은 품명·규격 조합은 중복 등록되지 않는다. |
| FR-16a | 품목을 품명·규격·별칭·POS 코드·바코드로 검색할 수 있다. 품명 일부(부분 일치)로도 검색되고, 공백 차이는 무시한다(예: "타이레놀 500mg"과 "타이레놀500mg"을 같은 것으로 찾음). 결과에는 품명·규격·기준 단위를 표시한다. 품목 관리 화면과 입고 화면이 같은 검색 기능을 쓴다. | 품명 일부만 입력해도 후보가 나오고, 두 화면에서 동일한 검색 결과가 나온다. |
| FR-17 | 관리자는 MOQ와 발주 단위를 설정한다(품목 등록 시 선택 입력으로도 가능). 거래처별 조건이 다르면 거래처 조건을 우선하고 없으면 품목 기본값을 쓴다. MOQ·발주 단위 등 발주 조건 설정은 관리자만 할 수 있으며, 이 권한은 화면과 서버(DB/RPC) 양쪽에서 강제한다. | 환산 정보 또는 MOQ가 없으면 임의값으로 확정하지 않고 입력 필요를 표시한다(추천 계산 시). 직원이 발주 조건 설정 API를 직접 호출해도 거부된다. |
| FR-18 | 거래처 기본정보(이름 등)와 프로모션 메모를 표시한다. 거래처 최소주문금액은 시스템에서 등록·표시·계산하지 않는다 — 대량구매 할인이나 금액 충족을 위한 추가 구매는 구매 담당자가 실제 주문 시 직접 판단한다(2026-09-23 최종 검수 반영, 이전 버전의 의약외품 5만원·의약품 20만원 참고값과 관련 경고 기능은 제거됨). | 거래처 화면에 최소주문금액 입력·표시·경고가 없다. |
| FR-19 | 특일 정보 API에서 공휴일 자료를 받아 저장하고 정기 갱신한다. 적용 기간과 마지막 성공 시각을 기록하며 관리자는 추가 휴무일을 설정할 수 있다. | 조회 실패를 휴일 없음으로 해석하지 않는다. 현재·다음 연도의 필요한 기간이 확보되었는지 확인한다. |
| FR-20 | 주문일 다음 날부터 토·일요일, 공휴일 및 적용되는 거래처 휴무일을 제외하고 두 번째 날짜를 도착일로 계산한다. 시각별 마감은 없다. | 토요일 주문은 다른 휴일이 없으면 화요일, 월요일이 휴일이면 수요일이다. |

### 예측과 사입 추천

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| FR-21 | 최신 판매 확정일까지 최근 180개 달력일을 분석 구간으로 사용한다. 해당 구간의 확인된 판매량과 0 판매를 회귀모델에 입력해 향후 날짜별 판매량을 산출한다. | 분석 기준일, 실제 관측일 수, 누락일 수, 모델 버전을 확인할 수 있다. |
| FR-22 | 표본이 부족하면 가용한 자료로 같은 모델의 산출 가능 여부를 확인한다. 다른 대체 예측식은 만들지 않는다. 산출 불가능하면 예측 없음으로 표시한다. | 신규 품목에 가상의 180일 판매량이나 임의 추천값을 생성하지 않는다. |
| FR-23 | 음수 예측은 원래 값과 경고를 표시하고 수량 계산에는 0을 사용한다. 소수 예측은 유지하다가 최종 발주 단위에서 올린다. | 예측이 -2개이면 경고가 있고 주문 수요에 -2를 더하지 않는다. |
| FR-24 | 실사 기반 추정 재고와 마지막 입고분 기준 소진 참고값을 구분한다. 마지막 입고분 기준 값은 기존 재고를 포함한 실제 재고로 표시하지 않는다. | 입고 100개, 이후 판매 80개라면 참고 잔량 20개이며 기준 입고일과 판매 기준일을 표시한다. |
| FR-25 | 예상 도착 전 수요와 수량 참고값을 비교해 사입 검토 대상을 만든다. 주말·공휴일 판매도 포함한다. 판매자료 기준일부터 현재까지 아직 반영되지 않은 수요를 빼먹지 않는다. | 자료 기준일이 어제이고 주문일이 오늘이면 그 간격을 계산에서 누락하지 않는다. 세부 일 경계는 D-01을 따른다. |
| FR-26 | 발주를 권유한 품목의 기본 수량은 MOQ와 예상 도착일부터 7개 달력일의 예측 판매 합계 중 큰 값으로 하고, 발주 단위 배수로 올린다. 이는 구매 수량 규칙이며 목표 총재고에서 잔량을 빼는 다른 공식으로 바꾸지 않는다. | MOQ 10개, 7일 수요 23개, 발주 단위 6개이면 24개를 제안한다. |
| FR-27 | 추천에 품목·규격, 참고 잔량과 기준 종류, 판매자료 기준일, 도착일, 예상 수요, MOQ·발주 단위, 추천량, 기존 입고 대기량 및 경고를 표시한다. | 관리자가 근거를 확인하고 수량 변경·보류·제외할 수 있다. |
| FR-28 | 판매·입고·실사·발주·휴일·발주조건 변경 시 관련 추천을 갱신한다. 발주가 끝난 항목은 단순 새로고침으로 미발주 항목처럼 재생성하지 않는다. | 관리자의 실제 발주 기록을 보존하고 추가 구매 검토 시 기존 대기량을 함께 표시한다. |

계산의 공통 기호는 다음과 같다. `ŷ(d)`는 날짜별 회귀 예측, `f(d)=max(0, ŷ(d))`, `A`는 예상 도착일, `M`은 MOQ, `U`는 발주 단위다. 모든 수량은 같은 기준 단위로 환산한다.

```text
7일 예상 수요 = Σ f(d), d = A부터 A+6일까지
추천 발주량 = U × ceil(max(M, 7일 예상 수요) / U)
```

### 체크리스트와 발주·입고 상태

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| FR-29 | 기본 화면은 사입 검토 체크리스트다. 관리자가 실제 발주 수량을 입력해 완료 처리하면 입고 대기로 이동한다. | 체크만으로 재고가 증가하지 않는다. 두 관리자가 같은 추천을 동시에 완료해도 발주가 중복 생성되지 않는다. |
| FR-30 | 입고는 품목별 현재 입고 대기량을 감소시킨다. 부분 입고는 잔량을 유지하고 전량 반영되면 진행 중 목록에서 숨기고 입고 반영 이력에 남긴다. | 발주 10개 후 입고 6개이면 4개 대기, 추가 4개이면 0개다. |
| FR-31 | 미발주·초과 입고도 실제 입고 전량을 반영하고 초과/미연결 입고 표시를 제공한다. 초과분을 미래 발주의 대기량에서 빼지 않는다. | 10개 대기 중 12개 입고는 대기 0개·초과 2개, 이후 새 발주 5개는 대기 5개다. |
| FR-32 | 발주 취소·수량 정정과 입고 정정 시 관련 품목의 대기량을 다시 계산한다. 입고를 개별 발주 건에 연결하는 입력은 요구하지 않는다. | 정정 전후 수량과 담당자를 확인할 수 있고 어느 개별 주문이 완료됐는지 임의로 표시하지 않는다. |

품목별 대기량은 시간순으로 발주 시 증가하고 입고 시 0까지 감소한다. 추가 입고 수량은 초과로 표시한다. 이 계산은 서버 내부에서 수행하며 직원은 입고 수량만 등록한다. 정정 시 영향받은 기간을 다시 계산하므로 현재 대기 숫자 하나만 저장하고 원천 기록을 버리면 안 된다.

| IR-07 | POS 파일 | 직원이 내보낸 파일을 수동 업로드한다. 최소 의미 필드는 판매일, 품목 식별자 또는 품명·규격, 수량이다. 지원 확장자·시트명·열명·반품·취소·전체/증분 여부는 실제 CatPOS 표본으로 확정한다. 제공된 Numbers 파일을 근거로 POS가 Numbers를 직접 출력한다고 가정하지 않는다. |
| IR-08 | 기기 내 OCR | 최소 결과는 원문 품목 후보, 규격 후보, 수량 후보, 미확인 여부다. 서버 전송 전 표준 품목 ID로 연결한다. 로컬 이미지 처리 가능 형식은 실제 iPhone 촬영·사진 선택으로 검증한다. 외부 OCR/LLM으로 사진을 전송하지 않는다. |
| IR-09 | 공휴일 API | 서버가 한국천문연구원 특일 정보 API를 호출해 날짜·명칭·공휴일 여부를 읽는다. 페이지 누락 없이 가져오고 토·일요일은 자체 계산한다. 인증 오류·실패·미제공 기간과 정상적으로 휴일이 없는 결과를 구분한다. 현재/다음 연도 자료를 매일 갱신하는 것을 초기 주기로 한다. |
| IR-10 | Supabase | Auth는 로그인, PostgreSQL은 업무자료, 서버 함수는 권한이 필요한 처리·공휴일 갱신·계산을 담당한다. DB 접근 정책과 함수에서 권한을 적용한다. 여러 화면의 변경 알림 후 필요한 자료를 다시 조회하고 재연결 시 최신 상태를 가져온다. |
| IR-11 | GitHub Pages | 정적 프론트를 배포한다. 프로젝트 하위 경로에서 이미지·스크립트·화면 이동과 새로고침이 동작해야 한다. 인증 후 복귀 주소와 서버 호출 허용 출처에 배포 주소를 설정한다. |

아래는 필수 논리 계약이다. URL 이름이나 REST/RPC의 선택은 구현자가 결정하되, 입력 의미·권한·중복 처리·응답 결과는 유지한다. 등록자는 로그인 세션에서 서버가 결정한다.

### DB에 필요한 논리 자료

| 자료 | 필수 내용·제약 |
|---|---|
| 계정 프로필 | Auth 사용자 ID, 관리자/직원 역할, 활성 상태. 비밀번호는 Auth에 맡긴다. |
| 품목/별칭/거래처 조건 | 규격과 기준 단위가 있는 표준 품목, 원천별 코드·이름, 단위 환산, MOQ·발주 배수. |
| 판매 집계/자료 기간 | 품목·판매일 조합을 유일하게 하고, 업로드가 확보한 날짜 범위를 별도로 기록한다. 파일 이름만으로 중복을 판정하지 않는다. |
| 입고/실사/발주 | 원천 사실의 수량·발생일·등록시각·담당자·정정 버전. 입고의 발주 ID 연결은 필수 아님. |
| 계산 기준점 | 종류(실사/최근 입고), 적용 일 경계, 과거 누적 판매량, 관련 자료 버전. 180일 정리 시 유지한다. |
| 추천/결정 | 생성 근거의 요약·모델 버전·수량·관리자 결정. 화면 표시와 원천 발주 기록을 구분한다. |
| 휴일 | 날짜·명칭·원천·조회 범위·마지막 성공 시각. 중복 날짜를 두 번 제외하지 않는다. |

## 5. 구현 전에 확정할 세부 항목

아래는 이전 논의에서 확정하지 않은 사항이다. 나머지 요구사항의 구현을 막지는 않으나 해당 계산과 검수 완료 전에 결정해야 한다.

- **D-01 일별 판매와 장중 입고·실사의 경계:** 일별 합계로는 입고 전후 판매를 정확히 나눌 수 없다. 제안은 최근 입고 기준 참고값에는 입고일 전체 판매를 보수적으로 차감하고, 실사 기반 수량은 마감 시점 기준으로 계산하는 것이다. 이는 초기 제안이며 확정 정책이 아니다. 도착일 판매를 도착 전 수요에 포함할지도 함께 고정해 검수한다. 구매 수요는 FR-26의 도착일부터 7일을 사용한다. IR-14는 확정된 일 경계를 저장해야 한다.
- **D-02 POS 형식·판매 단위:** 실제 파일에서 품목 코드, 거래 취소·반품, 파일 기간과 전체/증분 여부, 단위 환산을 확인한다. 지원 형식은 검증된 것만 명시한다.
- **D-03 회귀모델·품질 기준:** 180일 전체 분석, 음수 경고, 대체식 미개발은 확정이다. 회귀식·설명변수·산출 최소 표본·신뢰도 경고 기준은 실제 자료의 시간순 검증으로 정한다. 관측되지 않은 미래를 학습에 섞지 않는다. 검증 기준 확정 전 예측 정확도가 검증됐다고 표시하지 않는다.
- **D-04 iPhone 로컬 OCR:** 실기기에서 촬영·사진 형식·처리 시간·인식 품질·사진 미전송을 확인하고 엔진을 선택한다. 수동 입력은 기본적으로 제공하지만, OCR 검증을 생략하고 OCR 기능이 완성됐다고 처리하지 않는다.

|---|---|---|

| 업로드 완료일에 판매 없음 / 미업로드일 | 각각 0 / 자료 누락 | FR-08 |
| 입고 저장 요청 두 번 전송 | 입고 1건, 수량 1회 반영 | FR-13, NFR-05 |
| OCR 촬영부터 입고 저장까지 네트워크 검사 | 이미지·OCR 원문 전송 없음 | FR-11, NFR-08 |
| 휴일 없는 토요일 주문 / 월요일 휴일 | 화요일 / 수요일 도착 | FR-20 |

| iPhone 저장 후 관리자 PC 확인 | 정상 연결에서 최신 상태 동기화 | NFR-01~03, IR-10 |
| Supabase 중단 후 재개 | 성공하지 않은 저장을 완료로 표시하지 않음, 문서대로 재개·연결 확인 | NFR-12 |

개발 완료 시 소스·DB 변경 스크립트와 함께 POS 입력 규격, 실제 모델과 검증 결과, 환경변수 이름, 계정 발급·정지 방법, 무료 프로젝트 재개 방법을 저장소에 문서화한다. 비밀값과 실제 영업자료는 커밋하지 않는다. 별도 백업 절차는 납품 범위에 포함하지 않는다.
