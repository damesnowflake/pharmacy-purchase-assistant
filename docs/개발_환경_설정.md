# 개발 환경 설정

작성일 2026-09-23 (2차 갱신). 이 문서는 로컬에서 이 저장소를 실행·시험하고, 실제 Supabase·
Cloudflare 계정이 준비됐을 때 배포하는 방법을 정리한다.

## 프론트엔드만 띄우기 (Supabase 없이)

```bash
npm install
npm run dev
```

로그인 화면은 뜨지만 `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`가 없으면 실제 로그인은 되지
않는다. `.env.example`을 복사해 `.env.local`을 만들고 실제 Supabase 프로젝트 값을 채운다.

## 순수 계산 로직 검증 (Supabase 불필요)

```bash
npm test          # vitest, src/lib/*.ts의 40개 단위 테스트
npm run typecheck
npm run lint
npm run build
```

## Supabase 프로젝트 연결 후

1. Supabase 프로젝트를 만들고 `SUPABASE_URL`, `anon` 키, `service_role` 키를 받는다.
2. `supabase/migrations/0001_*.sql`부터 `0010_*.sql`까지 순서대로 SQL 편집기 또는
   `supabase db push`(Supabase CLI)로 적용한다. `0008`은 `pg_cron`, `0010`은
   `supabase_realtime` publication을 쓰는데 둘 다 Supabase 프로젝트에는 기본 제공되므로
   그대로 적용하면 된다(로컬 순수 PostgreSQL에서는 없으면 자동으로 건너뛰도록 만들어 뒀다).
3. `.env.local`에 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`를 채운다.
4. 최초 계정은 화면에서 만들 수 없다(FR-01~02). 셸에서 서비스 키로 발급한다.

```bash
SUPABASE_URL=https://xxxx.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=... \
npm run issue-account -- --email admin@example.com --name "관리자" --role admin
```

5. Edge Functions 배포:

```bash
supabase functions deploy holiday-sync
supabase functions deploy forecast-batch
supabase secrets set HOLIDAY_API_SERVICE_KEY=...   # 공공데이터포털 서비스 키
```

6. 두 Edge Function을 매일 자동 호출하려면(시스템_구조_설계.md: 02:00 공휴일 동기화,
   판매 업로드 후 즉시 forecast-batch), Supabase 대시보드의 Database → Cron에서 아래처럼
   `pg_net`으로 HTTP 호출을 예약한다(프로젝트별 URL·anon key가 필요해 SQL로 미리 커밋해 두지
   않았다):

```sql
select cron.schedule('holiday-sync-0200-kst', '0 17 * * *', $$
  select net.http_post(
    url := 'https://<project-ref>.supabase.co/functions/v1/holiday-sync',
    headers := jsonb_build_object('Authorization', 'Bearer <anon-or-service-key>')
  );
$$);
```

   `forecast-batch`는 판매 업로드 직후 프론트에서 `supabase.functions.invoke('forecast-batch')`
   로도 호출하므로(이미 `SalesUploadPage.tsx`에 연결됨), cron은 놓친 항목을 뒤늦게 처리하는
   보조 수단으로 5~10분 간격으로 예약하는 것을 권장한다.

7. `0008_maintenance_and_capacity.sql`의 `daily-maintenance-0300-kst` 작업은 순수 SQL
   함수(`run_daily_maintenance`)를 호출하므로 `pg_net` 없이 `pg_cron`만으로 마이그레이션이
   자동 등록한다(같은 마이그레이션 안에서 `cron.schedule`을 호출함).

## Cloudflare Pages 배포

1. Cloudflare 계정에서 Pages 프로젝트를 만들고 이 GitHub 저장소를 연결하거나(대시보드에서
   빌드 명령 `npm run build`, 출력 디렉터리 `dist`로 지정), `wrangler.toml`을 이용해
   `npx wrangler pages deploy dist`로 수동 배포한다.
2. GitHub Actions로 배포하려면 저장소 시크릿에 `CLOUDFLARE_API_TOKEN`,
   `CLOUDFLARE_ACCOUNT_ID`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`를 등록한 뒤
   `.github/workflows/deploy.yml`을 Actions 탭에서 수동 실행(workflow_dispatch)한다. 자동
   배포를 원하면 그 파일의 `push:` 트리거 주석을 해제한다.
3. 인증 후 복귀 주소·CORS에 실제 Pages 도메인을 Supabase Auth 설정에 등록해야 한다
   (시스템_구조_설계.md IR-11).

## 이번 개발 환경에서 확인한 것 / 못한 것

- Supabase CLI(`supabase`), Docker, Deno가 이 개발 환경에는 설치되어 있지 않아 `supabase
  start`로 로컬 스택을 띄우거나 Edge Function을 직접 실행해 보지는 못했다.
- 대신 로컬 PostgreSQL 16(Homebrew)에 `auth.users`/`auth.uid()`만 최소 스텁으로 채워
  마이그레이션 0001~0010 전체를 적용하고, 판매 업로드 전체 흐름·180일 롤업·재계산 큐 연결을
  포함한 핵심 RPC를 실제 SQL로 실행해 검증했다(이 과정에서 실제 버그 2건 발견·수정).
  Edge Function 2개(holiday-sync, forecast-batch)는 esbuild로 구문만 확인했고 실행은
  못했다. 자세한 내용과 남은 한계는 [미확인_항목.md](미확인_항목.md)에 있다.
