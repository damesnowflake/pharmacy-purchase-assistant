# 사입 추천 시스템 개발 작업지시서

이 서비스는 직원이 등록한 판매·입고 자료로 사입 검토안을 만들고, 관리자가 이를 확인해 직접 발주하도록 돕는다. 자동 발주 시스템이 아니다. 현장 업무를 불필요하게 세분화하지 않고 **판매 업로드, 입고 등록, 추천 검토, 발주 완료 표시**에 집중한다.

## 사용 방식

Windows 11의 CatPOS Cloud(팜페이) PC에서 직원이 하루 한 번 판매내역을 내보내 웹 서비스에 올린다. 직원은 iPhone에서 종이 입고장을 촬영해 OCR 결과를 확인하고, **품목과 실제 입고 수량**을 등록한다. 관리자는 집이나 약국의 Windows·macOS PC에서 추천 목록을 보고 발주한 뒤 완료 표시한다. 모든 기기에서 같은 최신 목록을 볼 수 있는 반응형 웹 서비스로 만든다.

사용자는 약 5명이다. 공개 가입 없이 사전 발급한 계정만 로그인한다. 계정은 지정된 마스터 계정 보유자 또는 백엔드 개발자가 직접 발급·비활성화한다. 일반 사용자에게 회원가입이나 계정 발급 화면은 제공하지 않는다. 서비스 사용 권한은 두 종류만 둔다.

- **관리자:** 품목·거래처 설정을 관리하고, 추천을 검토·수정하며 발주 완료를 표시한다.
- **직원:** 판매 파일을 업로드하고 입고 수량과 필요한 실사 수량을 등록·정정한다.

관리자와 발주 담당자는 동일한 권한이다. 자료를 누가 등록하거나 수정했는지는 기록한다.

## 판매와 입고 자료

POS 파일의 **판매일**을 그대로 사용한다. 분석에는 시·분·초가 필요하지 않다. 파일을 품목별·일자별 순판매수량으로 집계한다. 판매 기록이 없는 날은 0개로 취급하되, 판매 파일 자체가 누락된 날은 0개로 간주하지 않고 자료 누락으로 표시한다. 반품·취소가 파일에서 어떻게 표현되는지는 실제 파일을 보고 구현한다. 같은 자료의 중복 업로드로 판매량이 중복되지 않게 한다.

입고장 사진은 서버에 업로드하지 않는다. iPhone에서 촬영·OCR한 뒤 직원이 품목과 수량을 확인하고 그 결과만 보낸다. 사진은 전송이 성공한 뒤 기기에서 지운다. OCR이 틀리거나 기기에서 사용하기 어려우면 직접 입력할 수 있어야 한다. 하루에 여러 번 입고되어도 각 입고를 기록하고 품목별 수량에 모두 반영한다. 입고는 특정 발주 건과 연결하지 않는다.

POS·입고장에 적힌 이름이 달라도 같은 상품으로 묶을 수 있도록 품목마다 표준 ID와 별칭·규격을 관리한다. 확실하지 않은 품목 매칭은 직원에게 확인받는다.

## 공휴일과 예상 도착일

토요일·일요일·대한민국 공휴일은 배송하지 않는 날로 본다. 공휴일·대체공휴일은 공공데이터포털의 **한국천문연구원 특일 정보 API**에서 받아 정기 갱신한다. 거래처의 별도 휴무일은 관리자가 추가할 수 있다. 네이버 캘린더 연동은 필요하지 않다.

주문 시각은 고려하지 않는다. 주문일 **다음 날부터 배송 가능한 날을 두 번 센 날짜**를 도착예정일로 한다. 예를 들어 다른 휴일이 없으면 토요일 주문은 화요일 도착이고, 월요일이 공휴일이면 수요일 도착이다. 공휴일 자료를 가져오지 못하면 저장해 둔 최신 자료를 사용하고, 해당 기간 자료가 없으면 도착일에 경고를 표시한다. 주말에도 판매는 발생할 수 있으므로 도착 전 예상 판매량에는 주말·공휴일을 포함한다.

## 사입 추천

품목별 최근 **180일의 일판매량 전체**를 회귀분석에 사용해 향후 일별 판매량을 추정한다. 판매가 없는 날은 0이다. 예측값이 음수이면 경고를 보여주고, 수량 계산에서는 0으로 취급한다. 자료가 부족한 품목에 별도 예측식을 만들지 않고 신뢰도 낮음을 표시한다. 회귀 모델의 구체적 형태는 실제 판매자료로 검증해 결정한다.

현재 수량을 아는 품목은 마지막 실사 수량에 이후 입고를 더하고 판매를 뺀다. 기준 실사가 없는 품목도 서비스를 시작할 수 있다. 이때는 **마지막 입고분과 이후 판매량의 차이**를 사입 검토의 참고값으로 쓰며, 실제 총재고라고 표시하지 않는다. 판매량 상위 50개 품목은 통계적 판단을 우선하고, 나머지는 입고 시 실사를 우선한다.

예상 도착 전까지의 판매로 수량이 부족해질 것으로 보이면 검토 목록에 올린다. 기본 추천 발주량은 **품목 MOQ와 도착 후 약 7일간의 예상 판매량 중 큰 수량**이며, 발주 단위가 있으면 그 단위에 맞춰 올린다. 기존 재고와 아직 입고되지 않은 발주량을 함께 보여준다. 품목별 MOQ·발주 단위는 관리자가 등록·수정한다. 값이 없으면 임의로 확정하지 않고 입력이 필요하다고 알린다.

거래처별 최소주문금액은 설정할 수 있게 한다. 참고 기본값은 의약외품 5만원, 의약품 20만원이지만 거래처마다 다를 수 있다. 대량구매 할인이나 금액을 맞추기 위한 추가 구매는 관리자가 판단한다. 추천 수량은 제안이며, 관리자는 수정·보류·제외할 수 있다.

## 체크리스트

추천 품목은 **사입 검토** 목록에 표시한다. 관리자가 실제로 발주한 뒤 수량을 적고 체크하면 검토 목록에서 사라져 **발주 완료·입고 대기** 목록으로 옮겨진다. 이후 직원이 입고를 등록하면 품목별 발주량과 입고량을 비교한다. 전량 입고되면 진행 중 목록에서 사라지고 **입고 반영** 이력에 남는다. 일부만 입고되면 남은 수량은 계속 대기한다. 발주 완료 표시만으로 재고를 늘리지 않는다.

발주 없이 입고되거나 발주량보다 많이 입고된 경우에도 **실제 입고 수량 전부를 재고에 반영**한다. 관리자에게는 `초과/미연결 입고`로 보이게 한다. 발주·입고를 개별 건끼리 억지로 연결하거나 이후 발주에 자동 배분하지 않는다. 화면의 대기량은 특정 거래처의 배송 상태가 아니라 **품목별 발주량 대비 입고량**이다.

## 저장할 데이터와 보관

필요한 데이터는 다음 정도로 제한한다.

- 계정: 사용자, 관리자/직원 권한, 활성 상태.
- 품목: 표준 ID, 이름·규격·별칭, 분류, MOQ·발주 단위.
- 일별 판매: 날짜·품목·순판매수량 및 자료 업로드 완료 여부.
- 입고: 입고일/시각·품목·실제 수량·등록자.
- 실사: 실사 시각·품목·그 시점의 총 보유량·등록자. 실사 이전 입고를 다시 더하지 않는다.
- 발주: 발주일·품목·실제 발주 수량·거래처·취소/정정 기록.
- 추천: 제시 당시의 예측·재고 판단 근거, 추천 수량, 관리자 결정 및 상태.
- 휴일: 공식 공휴일 자료와 관리자가 추가한 거래처 휴무일.

POS 원본 파일·원본 행은 검증에 필요한 기간만, 최대 30일 보관한다. 회귀분석용 품목별 일판매량은 최근 180일 보관한다. 오래된 일별 집계를 지워도 실사·입고 이후 판매량 계산이 끊기지 않도록 **품목별 누적 판매 기준값**을 유지한다. 발주·입고·실사와 현재 진행 중인 상태는 30일이 지났다는 이유만으로 삭제하지 않는다. 사진과 OCR 원문은 서버에 저장하지 않는다.

## 구현 시 확인할 사항

실제 CatPOS 파일에서 품목·판매일·수량·반품을 읽는 방법, iPhone에서 사진을 서버에 올리지 않는 OCR 방식, 공공데이터포털 API 서비스 키와 응답 형식, 실제 판매자료에 맞는 회귀 모델은 구현 초기에 확인한다. 외부 자료가 누락되거나 품목 매칭이 불확실할 때는 조용히 계산을 확정하지 말고 직원 또는 관리자에게 알린다.

완성 검수에서는 동일 판매 파일의 중복 업로드 방지, 토요일 주문과 공휴일을 포함한 2영업일 계산, 부분 입고 시 대기 수량 유지, 초과 입고의 재고 반영, Windows·macOS·iPhone에서의 동시 사용을 확인한다.
