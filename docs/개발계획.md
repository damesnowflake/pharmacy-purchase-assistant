# 사입 추천 시스템 개발 계획

작성일 2026-09-23. 기준은 [소프트웨어 요구사항 명세서](소프트웨어_요구사항_명세서.md), 원문 blob `b142d9a7395a0da3650fa3fc2b6f28f9aed9e83f`다. 이 문서와 연결 문서는 구현을 위한 설계이며, 실제 서비스와 DB를 구축·배포한 결과는 아니다.

## 설계 문서

- [시스템 구조](시스템_구조_설계.md): 화면, 구성 요소, API, 인증, 배포, 장애 대응.
- [데이터베이스](데이터베이스_설계.md): 테이블, 자료형, 관계, 제약, 권한, 보관 정책.
- [상세 알고리즘](상세_알고리즘_설계.md): 판매 집계, OCR 정규화, 재고 참고값, 2영업일, 회귀분석, 추천 수량, 입고 대기량.

서비스의 사용 흐름은 판매 업로드 → 입고 등록 → 추천 검토 → 실제 발주 후 체크 → 입고 반영이다. 5명 규모의 단일 약국을 대상으로 하며 관리자·직원 두 권한만 둔다. 직원에게 물류 단계별 입력이나 입고와 발주 건의 연결을 요구하지 않는다.

## 기술 선택

프론트는 React·TypeScript·Vite의 정적 SPA, 데이터 조회 캐시는 TanStack Query, 표는 TanStack Table을 기본안으로 한다. DB·인증·서버 처리는 Supabase 무료 플랜의 PostgreSQL·Auth·Edge Functions를 사용한다. 실시간 알림은 변경된 데이터의 재조회를 유도한다. Redis, 별도 상시 실행 서버, 유료 LLM은 기본 구성에 넣지 않는다.

기기 내 OCR은 Tesseract.js의 한국어·영어 모델을 우선 시험한다. 표 인식 품질과 iPhone 메모리·속도를 실측한 후 채택한다. POS 파서는 실제 내보내기 형식을 확인해 고르고, 이미 제공된 Numbers 파일이 POS 원본 형식이라고 가정하지 않는다.

프론트 배포 대상은 Cloudflare Pages Free로 한다. GitHub 저장소의 정적 빌드를 배포하며, 데이터·인증은 Supabase가 담당한다. Pages의 월 500회 빌드는 코드 배포 한도이며 직원의 화면 조회나 업무 등록 횟수가 아니다. 호스팅 주소에 종속되지 않도록 구현하고 Supabase 인증 URL·CORS에는 실제 Pages 주소를 등록한다. [Cloudflare Pages 한도](https://developers.cloudflare.com/pages/platform/limits/)

## 구현 순서

기간은 개발자 1명이 집중 투입되고 자료·서비스 키를 제때 제공받는 경우의 작업량 추정이다. 외부 계정 발급 대기와 현장 자료 수집 시간은 별도다.

| 단계 | 작업 | 완료 기준 | 예상 작업일 |
|---|---|---|---|
| 1. 입력·계산 검증 | 실제 POS 파일, 입고장 표본, iPhone OCR, 판매 일 경계, 단위 환산, 회귀 실험 | 실제 표본을 일별 판매와 품목·수량으로 변환하고 한계 기록. 알고리즘의 기본안 확정 | 2~3일 |
| 2. 공통 기반 | Vite 앱, 로컬 Supabase, 스키마·RLS·RPC, 로그인, 운영자 계정 발급 스크립트 | 직원/관리자 권한 시험과 비활성 계정 거부. 비밀키 미포함 빌드 | 2~3일 |
| 3. 자료 등록 | 품목·별칭·단위, 판매 업로드, 입고·실사, 중복/정정, 일별 보관 정리, 원본·임시자료 만료 처리 | 반복 업로드·동시 저장·부분 실패로 수량이 중복되거나 사라지지 않고 원본·임시자료가 기한 내 정리됨 | 3~4일 |
| 4. 추천 계산 | 공휴일 수집, 도착일, 회귀모델, 소진 판단, MOQ/발주 단위, 결과 캐시 | 합의한 예제와 같은 값. 자료 누락·음수·표본 부족을 구분 | 3~4일 |

전체 예상은 14~20 작업일이다. 기본 입력과 DB가 검증되면 화면 작업과 공휴일·예측 구현은 분담할 수 있다. OCR 정확도·POS 형식·실제 판매 패턴이 예상과 다르면 해당 단계의 작업량을 다시 산정한다.

## 무료 플랜 용량 구현 기준

업무량 가정은 하루 발주 10건·입고 20건·판매 파일 1회, 30일에 각각 약 300건·600건·30회다. 이는 품목별 행 수나 화면 조회량을 뜻하지 않으므로 이 수치만으로 DB 크기나 전송량을 보장하지 않는다. Supabase Free의 기준 한도는 DB 500MB, 파일 Storage 1GB, 월 비캐시 전송량 5GB, Edge Function 월 50만 호출이다. 한도 변경 가능성을 고려해 배포 직전 공식 요금표를 재확인한다. [Supabase 요금표](https://supabase.com/pricing)

판매 파일은 영구 보관하지 않는다. 브라우저에서 가능한 범위까지 품목·판매일별로 집계하고 서버에서 검증한 뒤 일별 집계만 장기 저장한다. 원본 임시 보관이 필요한 형식·오류 처리라면 private Storage에만 두고 적용 또는 오류 검토 후 삭제하며, 최장 30일을 넘기지 않는다. 입고장 사진은 기기 내 OCR·확인 후 서버에 올리지 않고 품목·수량만 전송한다. 단, POS 원본의 행별 정정·중복 검증에 필요한 임시행과 메타데이터는 [DB 설계의 보관 정책](데이터베이스_설계.md)을 따른다.

최근 180일의 일별 판매량은 회귀 입력으로 보관하되 판매 0인 날짜의 행은 만들지 않고 조회 시 0으로 채운다. 180일 밖의 판매량은 품목별 누적으로 이월하여 마지막 입고분 차감 계산을 유지한다. 모델은 품목당 최신값만 보관한다. 발주·입고 및 정정 근거는 조용히 삭제하지 않는다. 조회 API는 화면에 필요한 품목·기간만 반환하고, 실시간 알림에는 전체 목록 대신 변경 신호만 보내 다시 조회하게 한다.

초기 자료 적재와 시험 운영 1개월 뒤 DB의 테이블·인덱스 크기, Storage 사용량, 월 전송량, 함수 호출량을 각각 측정한다. 운영 중 월 1회 확인하며 DB 또는 Storage의 70% 도달 시 원인 조사, 85% 도달 시 신규 적재 전망을 검토하고 관리자에게 알린다. DB 500MB 초과 시 읽기 전용 전환 위험이 있으므로 필수 이력을 임의 삭제하지 않고 원본 만료·중복 자료·인덱스·조회량을 먼저 점검한다. 무료 한도 내 유지가 불가능하면 관리자가 유료 전환 또는 수동 운영을 결정한다. 자동 백업은 도입하지 않는다. [DB 초과 동작](https://supabase.com/docs/guides/platform/database-size)

## 첫 구현에서 고정할 설계 기본안

아래는 운영자의 추가 승인으로 확정된 사항이 아니라, 요구사항의 미결 부분을 개발 가능한 수준으로 채운 제안이다. 실제 표본 검증 후 변경하면 모델·계산 버전과 문서도 함께 변경한다.

1. 회귀모델은 선형 시간 추세와 요일 변수를 포함하는 OLS를 사용한다. 같은 모델을 계속 쓰고 표본 부족 시 대체 예측식은 만들지 않는다.
2. 최근 입고분 소진은 최신 입고일의 입고 합계에서 그날부터의 판매를 차감하는 보수적 일 단위 지표다. 정확한 장중 잔량으로 표시하지 않는다.
3. 실사 수량은 등록 시점의 실제 수량으로 보관한다. 마감 기준 실사는 다음 날부터 실제 판매를 차감한다. 장중 실사는 당일 남은 판매를 추정한 뒤 다음 날부터 일별 실제 판매를 적용하며, 추정이 개입했음을 표시한다. 직원에게 마감까지 기다리도록 요구하지 않는다.
4. 도착 전 수요는 도착일 전체 판매까지 포함한다. 구매 수량은 요구사항대로 도착일부터 7일 수요를 쓰므로 두 구간이 도착일에 겹친다. 전자는 주문 시점 신호, 후자는 구매량 규칙이며 서로 합산하지 않는다.
5. 품목별 입고 대기량이 있는 경우 같은 추천을 계속 생성하지 않고 대기 화면에서 추가 부족 경고를 표시한다. 필요하면 관리자가 같은 화면에서 추가 발주를 기록한다.

## 검증과 산출물

수학·날짜 계산은 단위 시험, 입고·발주·판매 교체는 DB 통합 시험, 권한은 RLS/RPC 거부 시험, 전체 흐름은 브라우저 시험으로 확인한다. 예측 품질은 시간순 과거 검증으로 평가한다. 단순 평균은 검증용 비교에만 사용하며 운영 대체 모델로 추가하지 않는다.

핵심 예제는 토요일 주문의 화요일 도착, 월요일 휴일일 때 수요일 도착, MOQ 10·7일 수요 23·단위 6에서 추천 24, 10개 발주·12개 입고 후 새 발주 5개의 대기량 5, 180일 정리 전후 동일한 누적값이다. 실제 API·OCR·POS 검증과 단위 계산 예제 검증을 구분해 보고한다.

설계 작성 시 날짜 계산 2건, 수량 올림 1건, 대기량 계산 4건의 합성 예제를 실행해 기재한 결과와 일치함을 확인했다. 이는 설계식 예제 검증이며 실제 앱·DB·회귀모델·OCR·공휴일 API 연동 시험을 수행한 것은 아니다.

납품물은 앱 소스, 재현 가능한 DB 마이그레이션, 서버 함수, 환경변수 이름 예시, 익명 시험 데이터, 시험 결과, 계정 발급·정지 및 프로젝트 재개 문서다. 실제 영업자료·사진·비밀값은 저장소에 올리지 않는다. 사용자의 방침대로 별도 DB 백업을 만들지 않는다.

운영 전 필요한 외부 조건은 Supabase 무료 프로젝트의 소유 계정, Cloudflare Pages 프로젝트, 공휴일 API 키, 검증 가능한 POS 원본과 iPhone이다. 설계 작업을 위해 지금 이 계정이나 서비스를 생성할 필요는 없다.
