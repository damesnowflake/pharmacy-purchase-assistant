# 상세 알고리즘 설계

이 문서는 [요구사항 명세](소프트웨어_요구사항_명세서.md)의 계산을 개발 가능한 기본안으로 구체화한다. 회귀식과 장중 판매 환산은 이번 설계의 제안이며 실제 자료 검증 후 확정한다. 수학·규칙 기반 처리로 구성하고 LLM을 필수로 사용하지 않는다.

## 1. 공통 단위와 날짜

`T`는 주문일, `D`는 최신 완료 판매일(오늘까지의 완결 자료만), `A`는 예상 도착일이다. 모두 한국 날짜를 사용한다. 모델 입력은 D를 끝으로 최근 180개 달력일 중 실제로 보관·확보된 자료다. 판매자료가 오래됐다고 보관 범위를 과거로 무제한 늘리지 않는다.

`y(p,d)`는 품목 p의 날짜 d 순판매수량, `f(p,d)=max(0,예측값)`이다. 판매 원본 수량·MOQ·발주 단위·입고를 품목 기준 단위로 환산한다. 사용자 입력 2박스, 박스당 10개이면 계산 수량은 20개다. `mg`, `g`, `정` 같은 규격 문자를 임의로 포장 개수로 해석하지 않는다. 환산값이 없으면 사용자가 기존 단위 중 선택하거나 관리자가 설정한다.

## 2. 판매 파일에서 일별 집계 만들기

1. 파일 해시와 명시된 보고서 기간·형식을 읽고 실제 POS 형식에 맞는 파서를 선택한다.
2. 코드/바코드 → 확정 별칭과 규격 → 직원 선택의 순서로 품목을 연결한다. 날짜·수량·단위 오류를 수정한다.
3. 판매와 반품·취소를 POS 정의에 맞게 순판매수량으로 계산한다. 취소된 거래를 이미 제외한 파일에 취소를 다시 빼지 않는다.
4. `(품목,판매일)`로 합산하고 직원에게 기간·품목 수·오류를 보여준다. 확정하면 임시 행을 서버에 보낸다.
5. 전체기간 보고서는 해당 기간의 기존 집계를 새 결과로 원자적으로 교체한다. 단순 UPSERT로만 처리하면 새 파일에서 사라진 품목의 옛 판매가 남으므로 기간 내 기존 행을 함께 정리한다.
6. 보고서가 해당 날짜 전체를 포함한다고 확인된 경우에만 coverage를 complete로 기록한다. 행에 나타난 최소·최대 날짜만으로 전체 기간이 완전하다고 추정하지 않는다.

```text
for day in requested_period:
    if coverage[day] != complete: 값 = missing
    else if day < product.observed_from: 값 = not_observed
    else: 값 = sales_daily.get(product, day, default=0)
```

0은 실판매가 없었다는 관측이고 missing은 자료가 없다는 상태다. 학습과 소진 계산에서 구분한다. `observed_from`이 확인되지 않은 기존 취급 품목은 초기 자료 시작일을 관측 시작으로 쓰고 신규 취급 품목은 실제 시작일을 설정한다. POS가 월 합계만 제공하면 일별 회귀를 만들 수 없으므로 일별 내보내기 형식을 먼저 확보한다.

상위 50개 품목은 D를 포함한 최근 30개 달력일의 순판매량 합계를 내림차순으로 정렬해 정한다. 동률은 품목 ID 순서로 고정한다. 누락일이 있으면 관측된 합계와 확보 일수를 표시하며 완전한 30일 순위처럼 표현하지 않는다. 분석 단위는 품목별 기준 단위이고 임의로 매출액 순위로 바꾸지 않는다.

0020 구현에서는 D를 한국시간 오늘로 사용한다. `sales_priority_summary`가 양의 순판매량이 있는 활성 품목 중 최대 50개를 반환한다. 사입 검토 화면의 순위 목록 및 입고 행의 안내에 연결하며, 판매 업로드·상품 변경·날짜 변경 시 갱신한다. 상위는 통계 참고, 나머지는 입고 시 실사 권장이다. 이 구분으로 추천수량을 바꾸거나 입고 저장을 막거나 재고 기준점을 초기화하지 않는다.

## 3. OCR 후 품목·수량 정규화

브라우저 Worker에서 Tesseract.js 한국어/영어 인식을 시도한다. 자동 회전 옵션과 단어 좌표를 활성화하고 y좌표로 행을 묶어 품명·규격·수량 열 후보를 만든다. 별도 대비 보정은 아직 구현하지 않았다. 수량 헤더와 양옆 헤더의 x좌표로 경계를 정하고, 수량 열의 단일 양수 숫자만 후보로 사용한다. 좌표를 못 찾으면 명시적 `수량:` 라벨만 허용하며 나머지는 빈칸이다. 인식 신뢰도 60 미만은 직접 확인한다. 이 수치는 정확도 보장이 아닌 보수적 입력 기준이다.

`품명`, `규격`, `수량` 등 헤더와 열의 x좌표를 이용해 후보를 추출한다. 공급가·단가 열의 숫자가 수량으로 들어가지 않게 한다. 제공된 명세서처럼 이전 행의 품명이 생략되면 같은 표의 연속 규격 행인지 확인해 품명 후보를 이어 붙인다. 서로 다른 규격은 같은 상품으로 합치지 않는다. `1+1` 문구만 보고 수량을 두 배로 만들지 않는다.

매칭은 코드·바코드의 정확 일치, 규격을 포함한 확정 별칭, 유사 이름 후보 순서다. 유사도는 후보 정렬에만 쓰며 낮은 점수나 복수 후보를 자동 확정하지 않는다. 사용자는 한 화면에서 품목·수량을 수정하고 저장한다. 수량이 없으면 빈칸으로 두고 1개로 추측하지 않는다. 사진은 서버에 전송하지 않고 저장 성공 후 앱의 이미지 버퍼와 Worker를 해제한다. 사진 보관함 원본 삭제는 하지 않는다.

## 4. 2영업일 도착일

```text
arrival(order_date, supplier):
    day = order_date
    business_days = 0
    while business_days < 2:
        day = day + 1 calendar day
        require holiday coverage contains day
        if day is Saturday or Sunday: continue
        if day in official_holidays: continue
        if day in supplier_closed_dates[supplier]: continue
        business_days += 1
    return day
```

주문일이 토요일인지, 오전인지 오후인지는 별도 조건으로 넣지 않는다. 거래처를 선택하지 않으면 공통 공휴일 기준을 사용하고 거래처 선택 시 자체 휴무를 추가해 재계산한다. 공휴일 API 호출 결과가 정상인지와 전체 페이지를 받았는지 검증한 뒤 캐시를 교체한다. 실패하면 이전 성공 캐시를 유지한다. 필요한 기간의 캐시가 없으면 도착일은 미확정이며 임의로 모든 평일을 영업일로 계산하지 않는다.

## 5. 일별 수요 회귀

초기 모델은 절편·선형 시간 추세·요일 6개 더미를 갖는 OLS다. 한 주의 기준 요일을 하나 제외해 총 8개 계수를 사용한다.

```text
x(d) = [1, centered_scaled_day(d), I(Tue), I(Wed), ..., I(Sun)]
y(d) = 해당 날짜 순판매수량
beta = argmin Σ (y(d) - x(d)·beta)^2
raw_forecast(d) = x(d)·beta
f(d) = max(0, raw_forecast(d))
```

최근 180일의 관측값에 동일 가중치를 준다. 임의로 최근 30일만 쓰거나 오래된 값을 감쇠시키지 않는다. 완전한 데이터이면 180행 전부 사용한다. missing/not_observed는 0으로 넣지 않고 관측일 수와 누락을 기록한다. 모든 요일을 식별할 수 있고 설계행렬의 계수가 독립일 때만 학습하며 QR 분해 또는 검증된 수치 라이브러리를 사용한다. 역행렬을 직접 계산하는 구현은 피한다.

가용한 관측이 8개 계수를 추정할 만큼 충분하지 않거나 행렬 rank가 부족하면 `예측 없음`이다. 다른 식으로 바꾸지 않는다. 최근 180일을 다 확보하지 못한 품목은 `자료 부족`, 관측일 56일 미만은 추가로 `짧은 관측 기간`을 표시하는 것을 초기안으로 한다. 56일은 정확도 보증 기준이 아니라 약 8주 미만임을 알리는 표시 기준이다. 미래 예측이 음수면 원래 음수와 경고를 보관하고 발주 계산에는 0을 사용한다.

원자료의 음수 순판매는 반품 등으로 실제 발생할 수 있으므로 자동으로 0으로 바꾸지 않는다. 큰 반품·프로모션·일시적 품절은 일별 관측을 왜곡할 수 있으나, 원인 자료 없이 알고리즘이 임의 삭제하지 않는다. 판매가 없었던 이유를 모르면 미관측 수요를 복원할 수 없음을 검증 결과에 기록한다.

예측 검증은 마지막 28일의 각 날짜를 그 이전 자료만으로 예측하는 시간순 검증으로 한다. 이때 확보된 180일 안에서만 과거 학습 범위를 사용한다. MAE와 `Σ|오차|/Σ|실제값|`인 WAPE를 산출하며 분모가 0이면 WAPE는 N/A다. 단순 평균과 비교하는 것은 모델 평가용이며 운영 대체식으로 사용하지 않는다. 최종 운영 계수는 확보된 180일 전체로 다시 학습한다. 허용 오차는 표본 평가 보고서에서 확정하며 현재 설계만으로 정확도를 보장하지 않는다.

0021부터 실제 배치에서 평가하고 사입 검토의 `예측 품질·음수 경고` 화면에 연결한다. 평가 가능 일수와 부분 평가 여부, 단순 평균 대비 오차를 함께 보존한다. 추천이 생성되지 않아도 품목별 모델의 음수 원값·0 보정·경고를 조회할 수 있다. 실제 기기 검수는 1개월 이상 운영 피드백 후 개선하는 계획을 따른다. [운영 연결 및 피드백 계획](예측품질_운영연결.md).

판매 업로드 후 모델을 갱신하고 계수·관측기간·자료 버전·오차 요약만 저장한다. 입고·발주가 바뀔 때는 모델을 다시 학습하지 않고 필요한 날짜의 예측과 추천만 재계산한다.

## 6. 수량 참고값과 발주 시점

### 실사 없는 품목

초기 기본안은 **최신 입고일의 실제 입고 수량 합계**를 기준으로 하고, 그 날짜부터의 판매를 차감한다. 같은 날 여러 번 입고되면 그날 수량을 합쳐 일별 판매와 비교한다. 그 이전 날짜의 잔여 재고는 포함하지 않는 지표다. 최신 입고일을 B, 그날까지 등록한 입고 합계를 Q라고 하면 다음과 같다.

```text
실판매 반영 참고값 = Q - Σ 실제 순판매(B .. D)
도착일 말 예상 참고값 = Q - Σ 실제 순판매(B .. D)
                          - Σ 예측 판매(max(B,D+1) .. A)
```

B>D이면 실제 판매 합계는 0이다. B..D 사이에 업로드 누락이 있으면 정확한 소진 계산으로 확정하지 않고 자료 부족으로 표시한다. 오래된 실제 판매는 누적 기준값을 이용한다. 처음 입력하는 기준점이 이미 삭제된 과거 자료에 걸쳐 계산 불가능하면 확인을 요청한다.

입고일 이전 시각의 판매까지 차감될 수 있으므로 이 계산은 의도적으로 보수적인 일 단위 기본안이다. 실제 재고나 보장된 하한이라고 표시하지 않는다. 참고값이 음수여도 원값을 남겨 ‘최근 입고량보다 이후 판매량이 많음’으로 표시한다. 입고가 한 번도 없으면 참고값은 미확정이며 0으로 가정하지 않는다.

### 실사 있는 품목

실사 시각 C의 실제 수량 Q를 그대로 기록하고, 그 시각 이후 실제 입고·재고 조정을 더한다. 마감 후 실사임이 확인되면 다음 날부터의 실제 일판매를 뺀다. 장중 실사는 판매 시각 자료가 없어 같은 날 남은 판매를 정확히 알 수 없다.

장중 실사의 설계 기본안은 실사일의 **하루 예측량 전체를 남은 판매로 보수적으로 차감**한 일말 기준을 사용하는 것이다. `estimated_first_day_sales`와 모델 버전을 함께 저장하고 ‘장중 실사 보정 포함’으로 표시한다. 해당 일자의 실제 전체 판매를 나중에 다시 차감하지 않는다. 같은 날 실사 이후의 입고는 별도로 더한다. 모델이 없어 당일 보정이 불가능하면 그 기간의 자동 잔량 계산을 미확정으로 표시하되 입고·실사 등록은 저장한다.

```text
실사 기준 도착일 말 예상량
 = 실사 수량 + 실사 이후 실제 입고 + 실제 재고 조정
   - 장중 실사 당일 보수적 보정(마감 실사는 0)
   - 실사 다음 날부터 D까지의 실제 판매
   - max(실사 다음 날,D+1)부터 A까지의 예측 판매
```

실사와 입고가 같은 시각으로 입력되면 실사 시점에 포함된 사건 순서(`included_event_seq`)를 고정한다. 이미 수량에 포함된 입고를 다시 더하지 않는다. 보정 방식은 [개발 계획](개발계획.md)의 미확정 기본안이며 장중 수량의 정확성을 과장하지 않는다.

### 발주 검토 신호

도착일 말 예상 참고량이 0 이하이면 사입 검토 대상으로 표시한다. 도착일까지의 실제 영업 경과일을 모두 포함하므로 금요일·주말 주문은 월요일 주문과 다른 소비 기간을 갖는다. 품절 예상일은 미래 일별 예측을 차감하다 참고량이 처음 0 이하가 되는 날로 표시한다. 별도 안전재고 계수는 현재 요구사항에 없으므로 임의 추가하지 않는다.

입고 대기량은 현재 재고에 더하지 않는다. 대기량이 있으면 같은 자동 추천을 반복 생성하지 않고 대기 목록에서 부족 신호와 기존 대기량을 표시한다. 대기량만으로 정확한 도착 시점을 알 수 없으므로 자동으로 부족 신호를 숨기지 않는다. 관리자는 필요하면 추가 발주할 수 있다.

## 7. 실제 추천 수량

```text
M = 선택 거래처의 MOQ, 없으면 품목 기본 MOQ
U = 선택 거래처의 발주 단위, 없으면 품목 기본 발주 단위
W = Σ f(d), d=A..A+6
recommended = U * ceil(max(M,W)/U)
```

M·U는 기준 단위의 양수여야 한다. 계산값은 정확한 소수 연산으로 올리고 부동소수 오차 때문에 단위가 한 번 더 붙지 않게 한다. ‘낱개 주문 가능’이 확인된 품목만 U=1을 설정한다. 미등록 단위를 자동으로 1로 가정하지 않는다.

이 공식은 주문할 수량이다. 요구사항대로 재고를 빼서 7일 목표 재고까지 채우는 식으로 바꾸지 않는다. MOQ 10개·7일 수요 23개·단위 6개이면 24개, MOQ 30개·수요 23개·단위 6개이면 30개다. 예측 수요가 0이더라도 사입 신호가 있다는 이유만으로 무조건 MOQ 구매를 강요하지 않고 경고와 판단 근거를 표시한다. 예측 자체가 없으면 모델 기반 추천 수량도 없다.

도착일의 예측은 부족 여부를 판단하는 구간에도, 구매량의 7일 구간에도 나타난다. 이 둘을 합한 수량을 주문하지 않는다. 할인 등으로 수정한 최종 수량은 관리자가 입력하고 추천 수량과 구분해 저장한다. 거래처 최소주문금액을 맞추기 위한 조정은 시스템이 아니라 구매 담당자가 판단한다(2026-09-23 최종 검수로 관련 필드·경고 제거).

## 8. 발주·입고 대기량

품목별 사건을 `(occurred_at, recorded_seq)` 순서로 처리한다. 원천 사건은 보관하고 현재 대기 숫자는 재계산 가능한 캐시다.

```text
pending = 0
for event in active_quantity_events_in_time_order:
    if kind == order:
        pending += quantity
    if kind == receipt:
        applied = min(pending, quantity)
        pending -= applied
        extra_for_this_receipt = quantity - applied
    if kind == order_cancel:
        applied_cancel = min(pending, quantity)
        pending -= applied_cancel
        if applied_cancel < quantity: 정정 검토 경고
    # count, stock_adjustment는 물리 수량에만 영향, pending에는 영향 없음
```

입고 전량은 물리 수량에 반영한다. `extra_for_this_receipt`가 양수이면 관리자가 볼 초과/미연결 표시를 남긴다. 초과량은 다음 사건의 pending에서 빼는 잔액으로 저장하지 않는다. 특정 입고가 어느 주문에서 왔는지 추정해 FK로 연결하지 않는다.

한 품목의 review 추천에서 최초 발주가 생기면 waiting으로 이동한다. 기다리는 동안 추가 발주는 같은 품목 대기량에 더한다. 입고로 그 대기량이 0이 된 순간 해당 진행 중 항목을 received로 닫는다. 뒤의 새로운 부족 신호는 새로운 review 항목이다. 여러 거래처의 주문이 섞여도 화면은 품목별 총량이며 거래처별 배송 완료를 단정하지 않는다.

과거 사건을 정정하면 해당 품목의 사건을 다시 실행해 초과량·대기량과 파생 완료 상태를 갱신한다. 실제 발주와 당시 추천 근거는 그대로 이력에 남기고, 파생 상태가 바뀌면 수정 사실을 표시한다. 최초 버전은 전체 품목 사건 재실행으로 단순하게 구현하고 실제 성능이 필요할 때만 체크포인트를 추가한다. 발주 취소는 남아 있는 수량을 줄이는 현재 시점 사건이고, 원래 주문량 오입력 정정은 과거 사건의 수정이다.

| 사건 순서 | 최종 대기 | 표시 |
|---|---:|---|
| 발주 10 → 입고 6 | 4 | 입고 대기 |
| 발주 10 → 입고 6 → 입고 4 | 0 | 입고 반영 |
| 발주 10 → 입고 12 → 발주 5 | 5 | 앞선 입고 초과 2 |
| 입고 3 → 발주 5 | 5 | 첫 입고 미연결 3 |
| 발주 10 → 입고 6 → 잔량 취소 4 | 0 | 취소 이력 포함, 전량 입고로 표현하지 않음 |

전량 취소는 진행 중 목록에서 닫되 이력 이유를 ‘발주 취소’로 남긴다. 사용자 상태를 새 물류 단계로 늘리지 않고, 취소된 물건이 입고됐다고 표시하지 않는다.

## 9. 180일 정리와 정정

정리 전에 현재 기준점 이후의 삭제 대상 판매량을 `reference_sales_archives`로 이월한다. 전체 rollup과 기준점별 누적, daily 삭제를 동일 트랜잭션에서 처리한다. 반복 실행해도 이미 이월된 행은 다시 합산하지 않는다. 실제 차감값은 `reference_sales_total`에서 보존분과 남은 daily를 합산한다.

보관 중인 날짜의 정정은 일별 자료 교체로 반영한다. 삭제된 날짜는 원래 일별 수량이 없어 차이를 계산할 수 없으므로 재업로드를 거부한다. 삭제 구간의 기준점 경계를 알 수 없으면 `historical_sales_missing`으로 추천을 보류하고 새 실사를 안내한다. 과거 정정 API가 구현된 것으로 간주하지 않는다.

## 10. 계산 검증 사례

- 2026-09-12 토요일 주문, 별도 휴일 집합이 비어 있으면 2026-09-15 화요일 도착. 시험용 휴일 2026-09-14를 넣으면 09-16 도착. 이는 알고리즘용 합성 휴일 사례이며 실제 공휴일 조회 결과가 아니다.
- 최근 입고일 입고 100, 실제 판매 80, 도착 전 예측 수요 20이면 도착일 말 참고량 0으로 검토 대상이다. 일 10개 예상·MOQ 10·단위 1이면 구매량은 7일분 70개다.
- 월~금이든 주말이든 f(d)=10이면 7개 달력일 수요는 70이다. 배송일 제외 규칙을 판매량 계산에 적용하지 않는다.
- 발주량 10, 입고량 12, 신규 발주량 5이면 pending=5다. 수량 12를 현재 재고에 전부 반영한다.
- 0개 판매인 날짜와 업로드 없는 날짜는 학습 행에서 다르다. 음수 회귀 예측은 경고하면서 구매 수요에 0으로 반영한다.
- 같은 자료 버전으로 재계산한 값은 같아야 하며, 계산 중 입고가 갱신되면 이전 자료 버전 결과를 최신 추천에 덮어쓰지 않는다.
